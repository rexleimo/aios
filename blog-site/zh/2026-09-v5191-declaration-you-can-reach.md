# v5.19.1：一个真正够得着的声明通道

AIOS 的工作流策略是按声明驱动的：它读取显式的 `intent` 字段或 `/command` 前缀，绝不从散文里猜你想要什么。这个默认值是对的，但它有一道锋利的边。如果声明通道够不着，策略不会抱怨。它会退回自己的确定性默认值，永远不会选出任何 Provider。

这不是假设。它在这个仓库里真实发生过，而且持续了整整一个会话。

## 那个不存在的通道

`aios plan auto-gate` 只有一种方式能收到声明：消息里的 `/plan` 式前缀。前缀白名单是 `plan`、`team`、`subagent`、`harness`、`single`、`grill`、`spec`、`tickets`、`review`、`implement`、`debug`、`wayfinder`。里面没有 `/read-only`。

所以"只做检查"的回合（inspection-only）在 shell 里根本无法声明。规划层其实早就在读 `options.intent || options.explicitIntent` —— 读取侧一直存在，只是没有任何东西去产生它。新增的 `--explicit-intent <value>` 补上了这个缺口。

## 故意不加白名单

下一步顺理成章的想法是在 CLI 里用一张清单校验取值。我先写了这个方案，然后先去实测：

```
--explicit-intent read-only  -> direct  | explicit-direct-intent
--explicit-intent plan       -> planned | rex-capability-selected:software.planning.sequence
--explicit-intent readony    -> blocked | explicit-intent-unknown
```

策略对它不认识的词表已经 fail-closed 了。在 CLI 侧再抄一份，就是同一批词的第三张名字表，且零额外安全性。所以这个 flag 原样转发取值，让策略去判断。拼错取值的那条测试存在，是为了让这个理由以后不会被悄悄推翻。

## 路上的那个陷阱

在 Git Bash 里，以 `/` 开头的参数会被改写成 Windows 路径。`--message "/plan x"` 到达进程时是 `C:/Program Files/Git/plan x`，前缀永远匹配不上，决策静默退回默认值。我花了部分会话把这件事读成"声明通道坏了"。坏的是调用点。修法是 `MSYS_NO_PATHCONV=1`，教训是：先确认参数原样到达，再去怪产品。

## 守卫，以及它查出了什么

新 flag 需要一个测试。测试写了，全量回归跑了，结果很干净，而且用例总数和之前一模一样。新文件不在 `scripts/test-suites.json` 里，而那个文件是显式清单，不是 glob。套件从来没执行过它。

这就引出一个更大的问题：还有多少文件处在这个位置？

```
255  scripts/tests 下的 .test.mjs 文件
144  不在任何套件里
 82  任何测试入口都够不着
```

把这 82 个手动跑一遍：677 个用例，653 个通过，**23 个失败，涉及 14 个文件**。没有任何门禁报告过它们，因为没有任何门禁跑过它们。从外面看，一条健康的流水线和一套正在腐坏的测试是完全一样的。

于是有了这个守卫：它检查的是"可达性"而不是"是否注册"，因为 255 个文件里有 111 个本来就是按设计注册的，其余是通过 package.json 入口和 glob 接进来的。它把 82 个未接线文件留作漂移基线：新出现的未接线文件会失败，而不是被静默追加；而基线本身也无法腐化成一张万能豁免。它的牙齿是用变异验证的，不是用断言声明的：注入一个悬空的套件引用，只有那一条检查失败；新增一个未接线文件，守卫失败并点名它。

## 接下来

那 23 个失败是它们自己的工作。有些看起来依赖环境，有些像是状态假设，有些像是真的腐坏了。它们会被当作独立工作项，而不是塞进一个 patch 版本里悄悄埋掉。

这个版本想说的东西更小也更有用。如果声明是工作流了解你想要什么的方式，那这个声明就必须够得着。而如果一个测试跑不起来，就必须有东西把它说出来。
