# v5.19.0：给判定闸门装上身体

v5.18.0 发布的判定闸门，没人够得着。它有配置层、唯一出口的客户端、阈值映射和 CLI——唯独没有接到工作真正流经的地方。这一版把它接上了，而接线点本身就是重点。

## 够不着的闸门不算闸门

v5.18.0 的闸门在“默认关闭”这件事上是诚实的：三个条件同时成立才会有一个字节离开本机，并且有一条测试断言关闭时网络调用次数为 0。但“关闭”同时被当成了“做完”，而它并不是。一个只存在于你记得住的某条 CLI 子命令背后的能力，不是工作流里的闸门，是抽屉里的工具。

所以 v5.19.0 只加两个面，不多加：

| 面 | 触发时机 | 效果 |
| --- | --- | --- |
| `aios_judge` MCP 工具 | 仅在闸门已开启且凭据存在时 | 工具出现在 `tools/list` 中；关闭时它直接缺席，而不是“注册了再拒绝” |
| rex 阶段闸门 | 在某次 provider 证据推进 rex 阶段之前 | 证据不可验证时，推进被拦住（hold） |

两个面都不能生成内容，也都不能把已被拒绝的推进变成放行。这就是全部的设计约束：**判定只能收窄动作。**

## 面一——是缺席，不是拒绝

实现一个 opt-in 工具最直觉的做法是永远注册它，被调用时再返回“未开启”。我们做的是相反的：关闭时 `aios_judge` 根本不在工具表里。

这是对模型行为的一次刻意下注。一个**被列出来**的工具就是一个**会被试**的工具，而一个读到“未开启”的 agent 会开始和环境讲价——重试、猜配置键，或者更糟：凭空叙述它“本会收到”的那个判定。把它从表里拿掉，是消除可操作性，而不是和一个自动机争论。

拒绝路径依然存在，因为纵深防御很便宜：对已关闭工具发起的 `tools/call` 会被拒，并且有一条测试断言传输层记录到的调用次数为 0。这个工具既不可见，也不可动。

有一个后果值得直说。`enable` 写的是配置文件，而常驻的 MCP 进程每次 `tools/list` 都会重新读它——所以开启闸门不需要重启 MCP 服务；但凭据必须存在于**客户端**的环境里，这也是文档反复写“重启客户端”的原因。

## 面二——只有 advance 或 hold

rex 阶段闸门在某次 provider 证据被允许推进阶段之前，问一个 `noul` 问题：这份证据是否展示了可验证的完成，只依据证据本身所示来判断。

答案是两种结局之一。hold 是带原因的**正常结果**，不是崩溃——因为“我们无法验证这件事”是运维需要的信息，不是一个应当重试的错误。

闸门位于 host 侧，在 `scripts/lib/ctx-agent-core/run.mjs` 里、证据摄取之前的那一步。rex 子模块并不知道它存在。这一点很重要，有两个理由：子系统保持为状态机而不是策略引擎；闸门保持关闭时行为与之前完全一致——关闭路径在解析任何东西之前就返回 advance，并且有一条测试通过喂给它一份没有证据信封的输出、断言闸门仍报告 `disabled` 来钉死这个顺序。

### 让人不舒服的默认值

如果闸门已开启而厂商联系不上——500、超时、退避之后仍然 429——默认是 **hold**，不是放行。

这是 fail closed 的读法，而且它站得住脚：闸门是你主动开的，静默降级成“就当是”会把一个安全控制悄悄变成装饰。但这是个真实的取舍，所以它是一个配置键而不是藏起来的常量：如果你宁愿让厂商故障放行，把 `onJudgmentError` 设为 `"allow"`。默认是 `"hold"`，而且原因字符串总会写明应用了哪条策略。

## 我们弄错又公开修掉的两件事

**那个确定性 precheck 是冗余的。** 闸门拒绝为“没有可用引用”的证据花掉一次调用。事后读我们自己的信封解析器才发现，解析器本来就会拒绝空 evidence 数组与空 refs——所以在 runner 路径上这个 precheck 永远不会触发。我们保留了它（对直接传入已解析信封的调用方，它是承重的），但代码注释现在如实这么写。一个看起来在做它其实没做的事的检查，比没有这个检查更糟，因为它会误导下一个读代码的人。

**新增一个配置键可以静默关掉已有的闸门。** 把 `onJudgmentError` 做成必填，会让 v5.18.0 写出的每一份配置文件都校验失败——而校验失败的后果是 `disabled`。一个特意打开闸门的用户，会被一次升级关掉闸门，而且没有任何提示。所以这个键是“可选且带默认值”，并且有一条测试就是为这个场景命名的。

这两件事都是靠问“上一个版本写下的数据，撞上这段代码会是什么样？”发现的。这个问题比它听起来便宜得多。

## 仍然刻意关闭的部分

设计里的第三个触发点——用 Jev 对意图分类，从而把模糊请求路由到某个工作流——仍然没有实现，而且不是因为没时间。仓库契约禁止从文本推断 `intent`：一个模型自己填 intent 字段，那**就是**在推断。再找第二个模型来猜同一个字段，并不会让它变成一次声明。

另一件仍然开着的事：我们用的那把凭据在 TypeSafe 控制台上显示零次请求，尽管厂商自己的网关为每次调用返回了带签名的 `x-typesafe-request-id` 和 token 计数。那是厂商侧的问题，不是代码问题，我们把它记录下来而不是糊过去。

## 怎么开启

```bash
aios judgment status                 # 在你明确表态之前一直是 disabled
aios judgment enable typesafe        # 写 ~/.aios/judgment/config.json
aios judgment enable typesafe --probe   # 外加恰好一次计费调用，因为是你要求的
```

然后重启客户端，让它继承 `TYPESAFE_API_KEY`。`aios doctor typesafe` 会在不打印凭据值的前提下验证凭据存在性与 MCP 实时握手。
