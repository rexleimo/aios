# v6.0.0：工程标准内建——AIOS 构建软件，而不只是生成代码

> **Quick Answer：** 编码智能体生成的是"能跑"的代码；而这些代码通不过评审的原因每次都一样——边界违规、浅抽象、名不副实、没有测试安全网、没有工具链。这些是标准问题，而标准属于框架，不属于一篇没人会打开的 wiki。v6.0.0 发布 `aios-engineering-standards`：一套从经典书籍（Clean Architecture、软件设计哲学、代码整洁之道、程序员修炼之道、重构）推导出的质量基线，由 router 在**任何代码生产类 Provider 执行之前**加载，外加一份 Definition of Done——每处改动都要在既有证据契约之外再通过它。文档与参考文案（九本书单、免费合法资源、"书中观点 → AIOS 机制"映射）以中英日韩四语发布。

## 失败模式：能干的生成器，不工程的产出

工作流早就能写出正确的代码。测试跑了，diff 产出了，评审发生了。但回来的东西始终是*不工程*的：

1. **边界违规。** 业务逻辑直接伸手进框架、存储和 UI 细节。一个需求改动同时打破三层。
2. **浅抽象。** 一层层只做转发的 wrapper；为永远不会到来的未来预留的参数。净复杂度，零信息隐藏。
3. **命名与形态漂移。** 一个函数做四件事，名不副实，错误返回码在十几处被反复解码。
4. **没有安全网。** 没有测试，每次重构都是祈祷，每次评审都从零开始。
5. **没有工具链。** 没有 lint、没有 pre-commit、没有 CI——标准活在某个人的记忆里，而不是流水线里。

注意清单上**没有**什么："算法写错了"。模型能力从来不是瓶颈，**标准才是**。而参考材料的落地建议很直白：标准应该住在哪里——建一套开箱即用的模板，内置 Lint、Pre-commit Hooks、CI，把工程标准变成自动化流程，而不是一份文档。

## v6.0.0 改了什么

### 1. `aios-engineering-standards`——作为技能的质量基线

一个技能，框架加载，所有代码生产步骤共享。它把经典书单编码成可执行的规则：

- **架构边界（Clean Architecture）。** 源码依赖只指向内层；领域逻辑不 import 框架、驱动、UI 细节。高内聚、低耦合、最小接口。无法诚实地命名一个边界，说明设计没想清——回到设计选项，不要隔着雾硬写。
- **深层模块（《软件设计哲学》）。** 复杂度 = 理解成本 + 修改成本。小接口、深实现优于一层层薄转发。删除臆测的通用性。战略编程优于战术编程：每个改动都让代码库好一点。
- **代码基线（Clean Code / 程序员修炼之道）。** 命名表达意图；函数在同一抽象层级做一件事；错误携带上下文而不是返回码；DRY = 一个知识点一个权威表示；正交性 = 一个改动动一个地方。
- **测试基线。** 核心逻辑有自动化覆盖；重构只在绿色测试后进行；永远不为让构建通过而弱化断言。
- **工具链基线。** 新项目、新包、新模块必须带 lint、pre-commit hooks、CI、测试框架和结构化日志——标准由机器强制，不靠评审记忆。
- **文档基线。** consequential 改动记录一条简短 ADD：决策、适用条件、权衡、被拒选项。

### 2. Router 在代码生产类 Provider 之前加载它

`aios-workflow-router` 现在会在选中的 Provider 是 `rex-implement`、`rex-refactor-hardening`、`rex-code-review` 或 `rex-design` 时，**首先**加载本标准。完成门随之扩展：这些阶段要求**同时**通过 Provider 的证据契约**和**本标准的 Definition of Done。

这刻意不是一道 bolt 在侧面的新门。不存在"跳过质量"的路线——因为标准是 router 加载的，它和其他一切一样骑在证据驱动链上，每个阶段仍然只在真实证据上解锁。

### 3. `pre-edit-safety-gate` 按它核对变更形态

在一批改动的第一次编辑前，gate 本来就要决定变更形态（本地修改 / 扩展复用 / 重构提取）。现在它还会按基线核对该形态：依赖方向、深层模块启发式、命名、测试、工具链。设计证据和质量证据从此同源。

### 4. Definition of Done——八行，没有"感觉"

| # | 条目 | 通过标准 |
| --- | --- | --- |
| 1 | 行为符合验收 | 实现自检全"是" |
| 2 | 边界清晰 | 正确模块/层；依赖方向无伤；无接口泄漏 |
| 3 | 模块够深 | 新抽象隐藏真实细节；无薄转发、无预留参数 |
| 4 | 命名与函数 | 名实相符；单一抽象层级；错误处理统一 |
| 5 | 测试覆盖 | 核心路径自动化；断言未弱化 |
| 6 | 工具链 | Lint / pre-commit / CI / 日志达基线 |
| 7 | 文档 | consequential 改动有 ADD；契约已更新 |
| 8 | 证据 | 证据信封引用真实回执 |

任何一项"否"= 继续做——与实现自检相同的纪律，只是现在把工程基线装进了里面。

## 为什么这让 AIOS 不止是传统智能体

传统编码智能体帮你*写*代码。AIOS 运行整个工程闭环，而且已经跑了几个版本：计划前的需求对齐、记录被拒选项的设计决策、带场景回执的行为保持加固、基于 Fowler 坏味道基线和 fixed-point diff 的评审——每个阶段只在类型化证据上解锁。

v6.0.0 补上最后一块缺口：**"好"的含义从此是框架一等公民，而不是一句希望。** 智能体不需要记住你的规范文档——router 在它写第一行之前就把标准递到它手上，完成门再按标准检查结果。这就是代码生成器和软件工程系统的区别。
