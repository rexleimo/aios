# v6.3.0：/grill が本物のコマンドに、インタビューは自分で記録し、pi は自前で MCP キャリアを選ぶ

> **Quick Answer:** ひとつのリリースで 2 つの修正。第一に、AIOS の要件ヒアリングコマンド `/grill` はワークフローコアには存在しましたが、どこにも登録されていませんでした——どのクライアントも補完せず、パースしていたのは Claude Code の hook だけ。今は 7 クライアントに登録された薄いスキルになり、その裏の規律も欠けていた半分を補いました。確定したドメイン用語はリアルタイムで `CONTEXT.md` 用語集に、決着した意思決定は `docs/adr/` の軽量 ADR に書き込まれます。第二に、pi 0.99+ は内蔵 MCP 拡張を同梱し、別途インストールした `pi-mcp-adapter` と衝突して毎回起動時に警告を出していました。インストーラーは pi のバージョンを読んでキャリアを選びます。新しい pi では内蔵 MCP、アダプターはレガシーフォールバックのみ——しかも両者が読むのは同じ `mcp.json` です。

## 問題：打てないコマンドと、記憶を失うインタビュー

aihero.dev の `/grill-with-docs` の記事は、エージェントが計画についてヒアリングし、学んだことを記録する——用語は `CONTEXT.md` へ、意思決定は ADR へ——というスタイルを紹介していました。それを自分たちの実装と並べると、採点は正直なものではありませんでした。

**ヒアリングの半分は、とっくに持っていました。** `rex-requirements` は作業の中でインラインでヒアリングします。意思決定に関わる質問を一度にひとつ、すべての質問に推奨デフォルトを付け、3 ラウンドの予算で答えのない線はブロックではなく記録済みの仮定に変換します。しかし**書き残す**ことは決してありませんでした。`CONTEXT.md` があれば読むのに、書くものはリポジトリのどこにもなく、ヒアリングを生き延びた意思決定は揮発性のプラン状態に置かれたままでした。

**コマンドの半分はもっと酷でした。** `/grill`——`/plan`、`/spec`、`/tickets` ファミリー全員——はテキストの取り決めにすぎませんでした。ワークフローコアの正規表現、AGENTS.md の宣言プロトコル、Claude Code に配線された UserPromptSubmit hook。ZCode で `/grill` と打っても補完は何も出ません。何も登録されていなかったからです。

そして pi 0.99+ のマシンでは 3 つ目の厄介事：pi は 2026-09-29 に内蔵 `mcp` 拡張を同梱し、AIOS はその上にサードパーティの `pi-mcp-adapter` をインストールし続け、両者が `/mcp` を登録し、pi は毎回 `[Extension issues]` 警告を出した末にアダプターを黙って選んでいました。

## 変更内容

### /grill が登録済みスキルに

`skill-sources/grill/SKILL.md` は薄いエントリです。`explicit-intent: grill` を宣言し、rex-requirements のフローを実行し、その書き戻し規則を実行する。プロセスの詳細はあえて持ちません。食い違えば rex-requirements が勝つ——規律は一箇所だけに生きる。ビルドは全リポジトリサーフェス（`.codex/skills`、`.claude/skills`、`.agents/skills`…）に materialize し、frontmatter が約束する 7 クライアント（zcode、codex、claude、pi、qoder、hermes、workbuddy）のホームにインストールします。新しいセッションで `/` を打てば、そこにあります。

### インタビューは自分で書き残す

`rex-requirements` に「受け入れ基準の記録」と「最初のスライス」の間に一步追加されました。**その場でリポジトリに書き戻す**。回答がドメイン用語を確定させた瞬間、エージェントはリポジトリルートの `CONTEXT.md` 用語集に即座に upsert します。定義の一行と「なぜ」の一行。ユーザーが手書きした項目は決して書き換えません。澄清予算を生き延びた意思決定や明示的な判断は `docs/adr/NNNN-<slug>.md` になります。背景・決定・結果、番号は再利用しない。境界は規則に書き込まれています。記録された仮定は未検証であり、決して ADR にならない。決着した意思決定だけがなる。

これは第二のメモリシステムではありません。セッション横断のメモリは ContextDB レーンに残ります。pull 型で、強力で、recall が外れると沈黙する。`CONTEXT.md` と ADR は補完のレーンです。コードと一緒にバージョン管理され、誰も頼まなくても未来のすべてのエージェントと人間の目に触れる。違う質問には、違う保存先。

### pi は自分のバージョンから MCP キャリアを選ぶ

`resolvePiMcpMode()` は `pi --version` を読み、pi ≥ 0.99.0 なら `builtin`、それ以外なら `adapter` を返します。バージョン検出に失敗しても `adapter` に落ちる——常に安全なレガシーパスなので、オフラインのマシンも古い pi も以前とバイト単位で同じに動きます。両キャリアは同じ `~/.pi/agent/mcp.json` を読むため、AIOS 管理のサーバーエントリはキャリアに依存せず、サーバーは何も動きません。新しい pi ではインストーラーはアダプターを入れません。既に入っているアダプターは**報告されるだけ**（`installed-conflicts`、info レベル、任意の `pi remove npm:pi-mcp-adapter` 付き）。削除はセッションの挙動を変えるため、代わりには行いません。`aios doctor` も同じ分割を反映し、新しい pi で「Pi が MCP サーバーを読み込めない」という誤警告を出さなくなります。

## アップグレードノート

- `/grill` に移行作業は不要です。`aios init` を再実行（または pull 後にスキルを再同期）すれば現れます。それまでは旧来のテキスト取り決めパスがそのまま動きます。
- `CONTEXT.md` / `docs/adr/` は初回使用時に作成され、プロジェクトと一緒にコミットすべきものです。価値はコードと共にバージョン管理されることにあります。
- pi ≥ 0.99.0 の起動警告は情報レベルで無害です。アダプターはそのまま動きます。削除（`pi remove npm:pi-mcp-adapter`）は任意で、その後は内蔵 MCP に戻ります。`pi mcp list` をひと目見てからで十分です。
