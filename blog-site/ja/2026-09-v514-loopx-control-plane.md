# v5.14.0: LoopX コントロールプレーン + 孤児プロセス根絶

v5.14.0 は v5.11.0 以来の初リリースです。v5.12.0 のメモリ面と Pi クライアントに加え、長時間 harness のコントロールプレーン導入と、現場フィードバック由来の最後の二つのストール修正が入ります。

## 精算されるターン、祈るターンではない

LoopX のターンコントラクトを借り、すべてのプロバイダーターンが型付き envelope に精算されます：outcome、エビデンス、`effectRef` 冪等キー（実行トークン + ペイロードハッシュ）。独立の validator プロセスが書き込み前に再検証します——実行者は自己検証できず、重複副作用は拒否され、精算ジャーナルは追記専用です。

## 無人実行のリズム管理

should-run ゲートが毎ターン前に run、wait、ask、quiet を決定します：進捗がなければ cadence ラダーが起床間隔を緩め、24 時間デューティ比クォータは material ターンにのみ課金され、変化のないポーリングは静かに停止します。attended は不変、`--unattended` は厳格な opt-in、操作者ゲートへの応答は読み取り専用バイパス 1 回のみ、再入は明示 resume のみです。読み取り専用の `aios harness dashboard` が状態を静的 HTML に投影します。

## ターンが死んでも編集し続ける孤児

一部の検証タスクは正当に 30 分の既定タイムアウトを超えます。タイムアウト発火時、AIOS は直接の子プロセスしか殺しませんでした——下のプロバイダー CLI は孤児として生き続け、同じワークスペースを編集し続けるのに、ループは次のイテレーションへ進みます。2 エージェント、1 ワークスペース、誰も知らせません。

v5.14.0 は全ターンを detached で起動し、プロセスグループ全体を三段階で清掃します（SIGTERM グループ、猶予、SIGKILL グループ、生存確認）。SIGKILL 後も残る場合は並走せず停止します。検証が長いのは正当ですか？`--turn-timeout-ms` で上限を明示できます。

## 戻ってこないツール呼び出し

同種の問題は shell MCP にもありました：バックグラウンドの孫プロセスが stdout と stderr を掴んだままだと `close` が永遠に来ず、ツール呼び出しがハングします。shell サーバーも同じ三段階清掃を行い、`close` が来なくても強制精算します。タイムアウトはタイムアウトです。
