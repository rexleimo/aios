# v5.18.0：AIOS に TypeSafe Jev を——デフォルトはオフ、それは意図的

AIOS v5.18.0 は opt-in の**判断ゲート**を追加します。ワークフローが TypeSafe の System One モデル（Jev）に、狭く型付きの質問をひとつ投げ、校正された答えを受け取る仕組みです。同じリリースで、Gemini CLI の設定全体を静かに壊しうる不具合を修正し、内部キーがクライアントのスキルツリーへ漏れる frontmatter の問題も塞ぎました。

これは正直な版です。「前回のリリースは、見た目どおりのことがそもそもできていなかった」と気づいた話も含みます。

## 一言でいうと

| 質問 | 回答 |
| --- | --- |
| 認証情報はどう設定する？ | クライアントが実際に動く環境に `TYPESAFE_API_KEY` を設定し、**クライアントを再起動**します。コマンドは以下の 4 つ。 |
| TypeSafe 統合を入れれば Jev が答える？ | いいえ。導入されるのは**ドキュメント** MCP サーバーです。文書を検索するだけで、判断は生成できません。 |
| 導入すれば判断ゲートは有効？ | いいえ。`aios judgment enable typesafe` を実行するまでオフです。 |
| 認証情報やフラグが無いとどうなる？ | 何も送信されません。「答えは既知とみなす」フォールバックも存在しません。 |

## 最初に間違えていたこと

前回のリリースで `aios integration add typesafe` を出しました。コミットでスキルを固定し、sha256 を検証し、全クライアントに `typesafe-docs` を登録します。doctor は `verified` と報告しました。完成したように見えました。

そこで、導入された部品が実際に何をできるかを測りました：

| 部品 | できること |
| --- | --- |
| `typesafe-docs` MCP | ツールは 4 つ：`search_type_safe_ai`、`query_docs_filesystem_type_safe_ai`、`submit_feedback`、`read_typesafe`。**すべて文書検索で、推論ツールはありません。** |
| 同梱の `typesafe-ai` スキル | TypeSafe 公式のスキルです。`grep -c 'TYPESAFE_API_KEY\|POST\|curl\|systemone'` → **0**。概念を説明し、オンライン文書を指します。 |
| AIOS ランタイム | 呼び出し箇所はゼロ。 |

つまり前回のリリースは Jev の**地図**を導入しただけで、Jev 本体には一度も触れていませんでした。これはインストーラの不具合ではありません。計画文書は「認証情報を用いた TypeSafe API 呼び出し」を明示的に範囲外としていました。物語の欠落であり、このリリースがそれを埋めます。

教訓は一般化できます：**「統合が入っている」と「その機能が使える」は別の主張です。** doctor に値するのは後者だけです。

## 認証情報の設定

`TYPESAFE_API_KEY` が関わる唯一の認証情報です。AIOS は**存在の有無だけ**を確認し、値を読む・表示する・保存することはありません。設定は、コーディングクライアントが実際に動作する環境に対して行ってください。

最も多い失敗原因はスコープです。ある端末で `export` した変数や、別アカウントの *User* スコープに書いた変数は、すでに起動しているクライアントからは見えません。

**Windows —— 自分のアカウントに永続化：**

```powershell
[Environment]::SetEnvironmentVariable('TYPESAFE_API_KEY', '<あなたのキー>', 'User')
```

**Windows —— 全アカウント（管理者端末が必要）：**

```powershell
[Environment]::SetEnvironmentVariable('TYPESAFE_API_KEY', '<あなたのキー>', 'Machine')
```

**macOS / Linux：**

```bash
export TYPESAFE_API_KEY="<あなたのキー>"                                # 現在のシェルのみ
echo 'export TYPESAFE_API_KEY="<あなたのキー>"' >> ~/.bashrc            # 永続化
```

その後、**コーディングクライアントを再起動してください**。環境変数はプロセス起動時に一度だけ読まれます。すでに開いているクライアントは、後から設定した値を決して見ません。これが「統合は正しく入っているのに認証情報が無いと言われる」最大の原因です。

クライアントから何が見えるかを確認します：

```bash
aios integration doctor typesafe
```

認証情報の行は `present` か `unset` を報告し、値は表示しません。

## ゲートを有効にする

```bash
aios judgment status                    # あなたが意思表示するまで disabled
aios judgment enable typesafe           # ~/.aios/judgment/config.json を書き込む
aios judgment enable typesafe --probe   # ……計量対象の呼び出しを 1 回だけ送る
```

1 バイトでもマシンの外に出る前に、3 つの条件が同時に成立している必要があります：

| # | 条件 | デフォルト |
| --- | --- | --- |
| 1 | プロセス環境に `TYPESAFE_API_KEY` がある | 未設定 |
| 2 | `~/.aios/judgment/config.json` の `enabled: true` | `false` |
| 3 | セッションの呼び出し回数と入力長の予算が残っている | 20 回、20000 文字 |

いずれかが満たされない場合、呼び出し面は存在しません。リクエストは送られず、「答えは肯定とみなす」にフォールバックするコードパスもありません。`--probe` は、`ask` を直接使わずに AIOS が課金対象の呼び出しを行う唯一の経路であり、あなたが自分で打った場合にだけ動きます。

## 判断は提案であり、事実ではない

これが最も重要な設計判断です。Jev には何かを書き込む権限がありません。すべての結果はモデル、`x-typesafe-request-id`、トークン使用量、信頼度を伴い、ランタイムが許されているのは、それを設定済みのしきい値と比較することだけです。

| 裁定 | 条件 | 意味 |
| --- | --- | --- |
| `act` | 信頼度が `actFloor` 以上 | 確認せずに進めてよい |
| `confirm` | 2 つのしきい値の間 | まず人に確認する |
| `abort` | `confirmFloor` 未満 | 行動しない |

この 2 つの規則が、権威化を防ぎます：

- **リスクはしきい値を引き上げる方向にしか働きません。** 破壊的な変更は読み取り専用の操作より高い信頼度を必要とします。判断によって、ゲートが本来拒否する行為を AIOS が行う経路は存在しません。
- **`Noul` は設計上信頼度を持ちません。** API が返さないので、ゲートは与えられた確率をそのまま使い、信頼度らしい数値を製造したりはしません。

形状は値より先に検証されます。`choice` の答えが宣言していない選択肢を返した場合や、答えの `type` が送った質問と一致しない場合は、エラーです。無理に変換されることはありません。

## 同じリリースで直したもの

- **Gemini CLI 設定の修復。** AIOS は `~/.gemini/settings.json` に `startupTimeoutSec`（秒）を書いていました。Gemini は MCP サーバー項目を厳格モードで検証し、実際に受け付けるフィールドは `timeout`（**ミリ秒**）です。つまり 1 つの誤ったキーが**設定全体**を静かに無効化し、Gemini は起動を拒否していました。明示的なフィールド許可リストを持つ正規化器を（既存の ZCode 経路に倣って）追加し、すでに壊れていた 2 つの設定をバックアップ付きでその場で移行しました。
- **CRLF ファイルでの frontmatter 漏れ。** `parseFrontmatter` は `lines[0] !== '---'` で frontmatter の有無を判定していました。CRLF ファイルではその行が `'---\r'` になるため判定に失敗し、パーサはファイルをそのまま返し、AIOS の内部キー（`clients`、`scopes`、`repoTargets`……）がクライアントのスキルツリーへ直接漏れていました。ドキュメントが決して起きないと約束していたことです。パーサは入口で改行を正規化し、常に LF を出力するようになりました。AIOS 自身のハッシュ検証は、ハッシュ計算の**前に**改行を正規化していたため、ずっと警告を出していませんでした。
- **正直なクライアント対応表。** Gemini は検証済みの `cli` transport になりました。ZCode は `PATH` に CLI を持たない Electron クライアントだと判明しました。AIOS は stdio サーバーを `~/.zcode/cli/config.json` の `mcp.servers` に書き、ZCode はそこから読み取りますが、HTTP エントリには AIOS がまだ書き込まない `url` フィールドが必要なため、そこは手動手順のままです。ドキュメントはもう逆を示唆しません。
- **バージョン固定のサイトゲート 2 件。** `check:site-sync` は全言語にリリースブログ記事を要求します。このリリースの前は失敗していました。

## 証拠

ゲートはモックではなく、実際のエンドポイントに対してエンドツーエンドで検証しました：

```text
POST https://api.typesafe.ai/v1/systemone
date: Fri, 18 Sep 2026 11:54:33 GMT
HTTP/1.1 200 OK
x-typesafe-request-id: req_01a0b45e4b9d76d6b5346020c5df7aa9
{"model":"jev-1.13.0",
 "answers":{"severity":{"type":"score","score":2.94,"confidence":0.94,
            "probabilities":{"0":0.0,"1":0.01,"2":0.05,"3":0.94}}},
 "usage":{"input_tokens":325,"output_tokens":17}}
```

`x-typesafe-request-id` はサーバーが発行し、レスポンスには `istio-envoy` の上流時間ヘッダーも付きます。リクエストは実際に TypeSafe のゲートウェイを通り、計量されました。

無効時の経路も検証済みです。設定も有効化フラグも無い状態で、トランスポートが決して呼ばれないことをテストスイートが断言します。最も重視する性質なので、説明ではなく断言にしています。

## まだ答えられない部分

当社の TypeSafe コンソールは、この認証情報に対して**リクエスト 0 件**を示しています。にもかかわらず、すべての呼び出しにサーバー発行の request-id があります。照会できる使用量 API は存在せず（`/v1/me`、`/v1/account`、`/v1/usage` はすべて 404）、`Spend $0.00` は何の証明にもなりません。325 入力トークンは $0.042/MTok で $0.0000137 だからです。

最も可能性が高い説明は、このキーが私たちが見ているコンソールとは別の組織に属していることです。これは隠さず公開します。「ダッシュボードはゼロと言っている」は、問題になるまで無視されがちな類のシグナルだからです。課金のあるベンダーを自分のワークフローに組み込むなら、**呼び出しごとにベンダー自身の request id を記録してください**。請求の不一致に耐える唯一の証拠です。
