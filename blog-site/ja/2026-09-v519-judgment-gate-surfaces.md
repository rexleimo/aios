# v5.19.0：判断ゲートに身体を与える

v5.18.0 がリリースした判断ゲートには、誰も到達できませんでした。設定レイヤー、唯一の出口となるクライアント、判定のマッピング、CLI は揃っていましたが、作業が実際に流れる場所への接続だけが欠けていました。今回のリリースでそれを接続します。そして接続点そのものが本題です。

## 到達できないゲートはゲートではない

v5.18.0 のゲートは「オフであること」については誠実でした。三つの条件が同時に成立しない限り 1 バイトもマシンから出ず、無効時にネットワーク呼び出しが 0 回であることを断言するテストもありました。しかし「オフ」が「完成」の役目も兼ねてしまっており、実際には完成していませんでした。思い出さなければ使えない CLI サブコマンドの背後にしか存在しない能力は、ワークフローのゲートではなく、引き出しの中の道具です。

そこで v5.19.0 は面をちょうど二つだけ追加します：

| 面 | 発火するタイミング | 効果 |
| --- | --- | --- |
| `aios_judge` MCP ツール | ゲートが有効で、かつ資格情報が存在する間だけ | ツールは `tools/list` に現れます。無効のときは「登録済みだが拒否」ではなく、単に存在しません |
| rex ステージゲート | ある provider の証拠が rex ステージを進められるようになる前 | 証拠が検証不能なときは、進行が保留（hold）されます |

どちらの面も内容を生成できず、拒否された進行を許可に変えることもできません。これが設計上の制約のすべてです：**判断はアクションを狭めることしかできない。**

## 面 1 — 拒否ではなく不在

opt-in ツールを出す最も素直な方法は、常に登録しておき、呼ばれたときに「有効ではありません」を返すことです。私たちは逆にしました。無効の間、`aios_judge` はツール一覧にまったく存在しません。

これはモデルの振る舞いに対する意図的な賭けです。**一覧に載っている**ツールは**試される**ツールであり、「有効ではありません」を読んだエージェントは環境と交渉を始めます。再試行し、設定キーを推測し、さらに悪ければ「受け取るはずだった判断」を語り始めます。一覧から外すことは、自動機械と言い争うのではなく、行為の可能性そのものを取り除くことです。

拒否の経路も残しています。多層防御は安いからです。無効なツールへの `tools/call` は拒否され、トランスポートが記録した呼び出し回数が 0 であることを断言するテストがあります。ツールは不可視であり、かつ不活性です。

一つ、率直に述べておくべき帰結があります。`enable` が書くのは設定ファイルで、常駐する MCP サーバーは `tools/list` のたびにそれを読み直します。つまりゲートの有効化に MCP サーバーの再起動は不要です。ただし資格情報は**クライアント**の環境に存在する必要があり、だからドキュメントは「クライアントを再起動してください」と繰り返し書いています。

## 面 2 — advance か hold だけ

rex ステージゲートは、ある provider の証拠がステージを進めることを許される前に、`noul` の質問を一つ投げます：この証拠は検証可能な完了を示しているか。判断は証拠が示すものだけに基づきます。

答えは二つの結果のどちらかです。hold は理由を伴う**正常な結果**であり、クラッシュではありません。「これを検証できなかった」は運用者が必要とする情報であって、再試行すべきエラーではないからです。

ゲートは host 側、`scripts/lib/ctx-agent-core/run.mjs` の証拠取り込みの直前の一箇所にあります。rex サブモジュールはその存在を知りません。これが重要な理由は二つあります。サブシステムはポリシーエンジンではなく状態機械のままでいられること。そしてゲートを無効のままにすれば以前の挙動が完全に保たれることです。無効の経路は何かを解析する前に advance を返し、証拠エンベロープを含まない出力を渡してもゲートが `disabled` を報告することを断言するテストがその順序を固定しています。

### 居心地の悪い既定値

ゲートが有効で、ベンダーに到達できない場合 — 500、タイムアウト、バックオフを生き延びた 429 — 既定は **hold** です。進行ではありません。

これは fail closed の読み方であり、あなたが意図してゲートを有効にしたのだから妥当です。黙って「はいとみなす」に劣化させることは、安全制御を静かに飾りに変えてしまいます。ただしこれは現実のトレードオフなので、隠れた定数ではなく設定キーにしました。ベンダー障害を通したい場合は `onJudgmentError` を `"allow"` にしてください。既定は `"hold"` で、理由の文字列は常にどのポリシーが適用されたかを明示します。

## 途中で間違え、公開の場で直した二点

**あの決定的な precheck は冗長でした。** ゲートは「使える参照を持たない」証拠に呼び出しを消費しません。しかし後から自分たちのエンベロープ解析器を読むと、解析器自体が空の evidence 配列と空の refs をすでに拒否していました。つまり runner の経路では precheck は決して発火しません。残しました（解析済みエンベロープを直接渡す呼び出し元にとっては load-bearing です）が、コードコメントは今その事実を述べています。実際にはしていない仕事をしているように見えるチェックは、チェックが無いより悪いのです。次の読み手を誤らせるからです。

**新しい設定キーが既存のゲートを静かに無効化しえます。** `onJudgmentError` を必須にすれば、v5.18.0 が書いたすべての設定ファイルが検証に失敗します。そして検証失敗の帰結は `disabled` です。ゲートを意図して有効にした利用者が、アップグレードによって、何のメッセージもなくゲートを閉じられてしまいます。そこでこのキーは「任意・既定値あり」とし、まさにそのシナリオの名前を冠したテストを置きました。

どちらも「前のリリースが書いたデータが、このコードに出会うとどうなるか」と問うことで見つかりました。この問いは、聞こえのわりに安く済みます。

## 意図的にオフのままのもの

設計にあった第三のトリガー — 曖昧な要求を Jev に意図分類させてワークフローへルーティングする — は依然として未実装です。時間が足りないからではありません。リポジトリの契約は文章から `intent` を推論することを禁じています。モデルが自分で intent フィールドを埋めるなら、それは**まさに**推論です。同じフィールドを推測させるために二つ目のモデルを呼んでも、それは宣言にはなりません。

もう一つ未解決のままなのは、私たちが使った資格情報について TypeSafe のコンソールがリクエスト 0 件を示すことです。ベンダー自身のゲートウェイは呼び出しごとに署名済みの `x-typesafe-request-id` とトークン数を返しているにもかかわらず、です。これはコードの問題ではなくベンダー側の問題であり、覆い隠すのではなく記録しています。

## 有効にする

```bash
aios judgment status                 # あなたが明示するまで disabled
aios judgment enable typesafe        # ~/.aios/judgment/config.json を書き込みます
aios judgment enable typesafe --probe   # さらに、あなたが求めたので計量対象の呼び出しをちょうど一度
```

その後クライアントを再起動して `TYPESAFE_API_KEY` を継承させてください。`aios doctor typesafe` は資格情報の値を表示せずに、存在確認と MCP のライブハンドシェイクを検証します。
