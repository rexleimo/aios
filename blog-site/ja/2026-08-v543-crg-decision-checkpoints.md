# v5.4.3：CRG 決定チェックポイント、Worker Journal リネーム、冪等な `aios init`

> **クイックアンサー：** v5.4.3 はワークフロー層を構造的に安全にする小規模リリースです。`aios-workflow-router` と `rex-workflow` は code-review-graph（CRG）の決定チェックポイントを実行します——編集前に影響範囲を確認、コード変更前にテストの存在を確認、各段階の終了後に実際の変更を検証——そして CRG 未導入時は `rg` + ファイル読み取りに优雅にフォールバックします。solo harness ジャーナルディレクトリは `solo-harness` → `worker-journal` にリネームされ（旧ディレクトリは自動移行）、`aios init` には `--yes` / `--retry` / `--force` が追加され冪等なセットアップと更新が可能になりました。

## なぜ決定チェックポイントが重要か

依存関係を見ずにコードを編集するエージェントは、サイレントリグレッションの最大の原因です。従来のワークフローは「何をするか」（計画・実装・検証）だけを指示し、触る前に「どう調べるか」を教えていませんでした。v5.4.3 はワークフロースキルに4つの CRG チェックポイントを組み込むことでこれを修正します：

1. **作業前** —— `get_minimal_context` が約100トークンでプロジェクトコンテキストと次のステップを提示。
2. **編集前** —— `get_impact_radius` が変更対象ファイルの影響範囲を確認。`query_graph(tests_for)` がテストの存在を確認（なければ先にテストを書く）。
3. **コード検索時** —— `semantic_search_nodes` / `query_graph` が盲目的な grep + 読み取りを置き換え、高速かつ省トークン。
4. **各段階の終了時** —— `detect_changes` が実際の影響が意図どおりかを検証（自己申告ではなく）。

プロジェクトに CRG がない場合はその事実を記録し、`rg` + ファイル読み取りにフォールバックします——ワークフローをブロックせず、グラフの証拠を偽装もしません。

## Worker Journal リネーム

solo harness ジャーナルディレクトリは、既存のモジュール命名（`solo-journal`）に合わせて `solo-harness` から `worker-journal` に変更されました。セッション成果物は `artifacts/worker-journal/` に配置されます。既存の `solo-harness` ディレクトリは初回読み取り時に自動移行され——手動操作もデータ損失もありません——solo worktree の一時プレフィックスも新名に追従します。

## 冪等な `aios init`

`aios init` は以下のオプションをサポートします：

- `--yes` —— 対話確認をスキップ（CI / 無人インストール）。
- `--retry` —— 未インストールのコンポーネントから再開。
- `--force` —— インストール済みでも全て再インストール。

これらのオプションは新しい `install-state` モジュールに支えられ、コンポーネントのインストール状態を追跡するため、中断したセットアップは最初からやり直すのではなく再開できます。

## あなたがやること

- 既存インストール：`aios update` だけで完了。リネームの移行は自動です。
- スクリプトや CI で `aios init` を実行する場合：`--yes` で対話プロンプトをスキップできます。

## FAQ

### このリリースで CRG ツール自体は変わりましたか？

いいえ。code-review-graph MCP サーバーは変わりません。v5.4.3 が変えたのはワークフロー層がいつ・どのようにそれを呼ぶかです。CRG をインストールしなくても従来どおり動作します。

### 既存の `solo-harness` セッションデータは失われますか？

いいえ。移行は初回読み取り時にディレクトリをリネームし、全ファイルを保持します。旧名はレガシー検索としてのみ使われます。

### 詳細はどこで確認できますか？

[変更履歴](https://cli.rexai.top/ja/changelog/) に v5.4.3 が全ロケールで記載されています。

「変更したいこと」と「変更されたことの検証」のループを小規模リリースで締め付けることが、長期実行エージェントの信頼性を大きく高めます。
