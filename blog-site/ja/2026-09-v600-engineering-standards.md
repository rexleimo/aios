# v6.0.0：エンジニアリング基準の内蔵——AIOS はコードを生成するだけでなく、ソフトウェアを構築する

> **Quick Answer：** コーディングエージェントが生成するのは「動く」コード。それでもレビューを落ちる原因は毎回同じ——境界違反、浅い抽象、嘘をつく名前、テストの安全網なし、ツールチェーンなし。これらは基準の問題であり、基準は誰も開かない wiki ページではなくフレームワークに属する。v6.0.0 は `aios-engineering-standards` を出荷する：古典的な書単（Clean Architecture、A Philosophy of Software Design、Clean Code、The Pragmatic Programmer、Refactoring）から導出した一つの品質基準を、router が**どのコード生産 Provider の実行より前**に読み込み、Definition of Done——すべての変更が既存の証拠契約に加えて通過しなければならないもの——を添えて。ドキュメントと参考資料（九冊の書単、無料で合法なリソース、「書籍の原則 → AIOS の仕組み」マッピング）は en/zh/ja/ko で提供。

## 失敗モード：有能な生成器、工学されていないアウトプット

ワークフローは正しいコードを書くことができていた。テストは走り、diff は出て、レビューは行われた。それでも戻ってくるものは常に*工学されていなかった*：

1. **境界違反。** ビジネスロジックがフレームワーク、ストレージ、UI の詳細に直接手を伸ばす。一つの要件変更が三層を同時に壊す。
2. **浅い抽象。** 転送するだけの wrapper の積層。決して来ない未来のために予約されたパラメータ。純粋な複雑さ、情報隠蔽ゼロ。
3. **命名と形の漂流。** 四つのことをする関数、嘘をつく名前、十二か所でデコードされるエラーコード。
4. **安全網なし。** テストがないので、リファクタリングはすべて祈祷、レビューは毎回ゼロから。
5. **ツールチェーンなし。** lint も pre-commit も CI もない——基準は誰かの記憶の中にあり、パイプラインの中にない。

リストに**ない**ものに注目してほしい：「アルゴリズムが間違っていた」。モデル能力は決してボトルネックではなかった。**基準が**ボトルネックだった。そして参考資料の実地アドバイスは、基準が住むべき場所について厳しい：lint、pre-commit フック、CI を内蔵した、開けば使えるテンプレートを建てよ——工学基準を自動化パイプラインにせよ、ドキュメントにするな。

## v6.0.0 で変わったこと

### 1. `aios-engineering-standards`——スキルとしての品質基準

一つのスキル。フレームワークが読み込み、すべてのコード生産ステージが共有する。古典的な書単を実行可能なルールに符号化する：

- **アーキテクチャ境界（Clean Architecture）。** ソース依存は内側にのみ向かう。ドメインロジックはフレームワーク、ドライバ、UI の詳細を import しない。高凝集・低結合・最小インターフェース。境界を誠実に命名できないなら、設計は考え切れていない——霧の中を書き進めるのではなく、設計オプションに戻る。
- **深いモジュール（A Philosophy of Software Design）。** 複雑さ＝理解コスト＋変更コスト。小さなインターフェースと深い実装は、薄い転送の積層に勝る。投機的汎用性を削除する。戦術的より戦略的プログラミング：すべての変更でコードベースを少し良くする。
- **コード基準（Clean Code / The Pragmatic Programmer）。** 名前は意図を表す。関数は一つの抽象レベルで一つのこと。エラーは戻りコードではなくコンテキストを運ぶ。DRY＝一知識一権威表現。直交性＝一変更一場所。
- **テスト基準。** コアロジックは自動カバレッジを持つ。リファクタリングは緑のテストの後でのみ。ビルドを通すために断言を弱めない。
- **ツールチェーン基準。** 新しいプロジェクト・パッケージ・モジュールは lint、pre-commit フック、CI、テストフレームワーク、構造化ログを出荷する——基準は機械が強制し、レビュー記憶ではない。
- **ドキュメント基準。** 重要な変更は短い ADD を記録する：決定、適用条件、トレードオフ、却下されたオプション。

### 2. Router がコード生産 Provider の前に読み込む

`aios-workflow-router` は、選択された Provider が `rex-implement`、`rex-refactor-hardening`、`rex-code-review`、`rex-design` のいずれかのとき、本基準を**最初に**読み込む。完了門は拡張された：これらのステージは Provider の証拠契約**と**本基準の Definition of Done の**両方**を要求する。

これはわざと横に bolt された新しい門ではない。「品質スキップ」ルートは存在しない——基準は router によって読み込まれ、他のすべてと同じ証拠駆動チェーンに乗り、各ステージは依然として実証拠の上でのみ解放される。

### 3. `pre-edit-safety-gate` が変更形状を它に照らす

一批の最初の編集の前、gate はすでに変更の形（ローカル変更／拡張・再利用／リファクタ抽出）を決めている。それが今や基準でも照合される：依存方向、深いモジュール発想、命名、テスト、ツールチェーン。設計証拠と品質証拠は同じ源から来る。

### 4. Definition of Done——八行、感覚なし

| # | 項目 | 合格基準 |
| --- | --- | --- |
| 1 | 振る舞いが受け入れ基準を満たす | 実装セルフチェックがすべて「はい」 |
| 2 | 境界が明確 | 正しいモジュール/層。依存方向無傷。インターフェース漏洩なし |
| 3 | モジュールが十分深い | 新しい抽象が実のある詳細を隠す。薄い転送も予約パラメータもない |
| 4 | 命名と関数 | 名前が実態と一致。単一抽象レベル。エラー処理統一 |
| 5 | テストカバレッジ | コアパス自動化。断言は弱められていない |
| 6 | ツールチェーン | lint / pre-commit / CI / ログが基準を満たす |
| 7 | ドキュメント | 重要な変更に ADD。契約を更新済み |
| 8 | 証拠 | 証拠信封が実回執を引用 |

どれか「いいえ」なら作業を続ける——実装セルフチェックと同じ規律で、今や工学基準がその中に入っている。

## なぜこれが AIOS を伝統的エージェント以上のものにするか

伝統的なコーディングエージェントはコードを*書く*のを助ける。AIOS は工学ループを回すし、もう数バージョン前から回している：計画前の要件整合、却下オプションを記録する設計決定、シナリオ回執付きの行動保存硬化、Fowler スメル基線と fixed-point diff に対するレビュー——各ステージは型付き証拠の上でのみ解放される。

v6.0.0 は最後の隙間を埋めた：**「良い」とは何かが、希望ではなくフレームワークの一等市民 になった。** エージェントがあなたのスタイルガイドを覚えておく必要はない——router が一行書く前に基準を手渡し、完了門が結果を基準で照合する。これがコード生成器とソフトウェア工学システムの違いだ。
