# v5.19.1：本当に手の届く宣言チャネル

AIOS のワークフロー方針は宣言駆動です。明示的な `intent` フィールドか `/command` 接頭辞を読み取り、散文から意図を推測しません。この既定値は正しく、そして鋭い刃があります。宣言チャネルが届かなければ、方針は文句を言いません。決定論的な既定値に戻り、Provider が選ばれることはありません。

これは仮定の話ではありません。このリポジトリで、セッション一つ分まるごと起きました。

## 存在しなかったチャネル

`aios plan auto-gate` が宣言を受け取れる方法は一つだけでした。メッセージ内の `/plan` 形式の接頭辞です。接頭辞の許可リストは `plan`、`team`、`subagent`、`harness`、`single`、`grill`、`spec`、`tickets`、`review`、`implement`、`debug`、`wayfinder` です。`/read-only` はありません。

そのため、検査のみのターンは shell からは宣言できませんでした。計画レイヤーはすでに `options.intent || options.explicitIntent` を読んでいました。読み取り側は存在し、それを生成するものが何もなかったのです。新しい `--explicit-intent <value>` がその欠落を埋めます。

## 許可リストを意図的に置かない

次に思いつくのは、CLI 内で値を一覧と照合することです。その案を書き、その前に実測しました：

```
--explicit-intent read-only  -> direct  | explicit-direct-intent
--explicit-intent plan       -> planned | rex-capability-selected:software.planning.sequence
--explicit-intent readony    -> blocked | explicit-intent-unknown
```

方針はすでに、知らない語彙に対して fail-closed で動きます。CLI 側に写しを置けば、同じ語の三つ目の名前表になり、安全性は一切増えません。したがってこのフラグは値をそのまま転送し、判断は方針に任せます。誤入力のテストが存在するのは、この理由が後から静かに覆されないようにするためです。

## 途中の罠

Git Bash では、`/` で始まる引数が Windows のパスに書き換えられます。`--message "/plan x"` はプロセスに `C:/Program Files/Git/plan x` として届き、接頭辞は決して一致せず、判断は静かに既定値へ戻ります。セッションの一部を、これを「宣言チャネルが壊れている」と読み取ることに費やしました。壊れていたのは呼び出し側です。修正は `MSYS_NO_PATHCONV=1` であり、教訓は「製品を疑う前に、引数がそのまま届いたか確認する」ことです。

## ガードと、それが明らかにしたもの

新しいフラグにはテストが必要でした。テストを書き、全量リグレッションを実行し、結果はクリーンで、テスト件数は以前とまったく同じでした。新しいファイルは `scripts/test-suites.json` に載っておらず、そのファイルは glob ではなく明示的な一覧です。スイートはそれを一度も実行していませんでした。

そこから大きな疑問が生まれます。同じ立場にあるファイルは他にいくつあるのか？

```
255  scripts/tests 配下の .test.mjs ファイル
144  どのスイートにも入っていない
 82  どのテスト入口からも到達できない
```

その 82 個を手で実行すると、677 テスト、653 成功、そして 14 ファイルにまたがる 23 の失敗でした。どのゲートもこれを報告していません。どのゲートもこれを実行していないからです。外から見れば、健全なパイプラインと腐りつつあるテスト群はまったく同じに見えます。

そこから生まれたのがこのガードです。検査するのは「登録」ではなく「到達可能性」です。255 個のうち 111 個は設計上登録されており、残りは package.json のエントリと glob で接続されているからです。82 個の未接続ファイルはドリフトの基準線として保持し、新たに未接続のファイルが現れたら静かに追記されるのではなく失敗し、基準線自体も万能の免除に腐ることはできません。その歯は断言ではなく変異で検証します。懸空のスイート参照を注入すればその検査だけが失敗し、未接続ファイルを追加すればガードは失敗し、そのファイル名を告げます。

## 次にやること

23 の失敗はそれ自体が仕事です。環境依存に見えるもの、状態の前提に見えるもの、そして本当に腐敗しているように見えるものがあります。パッチリリースの中に埋めるのではなく、独立した作業項目になります。

このバージョンの主張はもっと小さく、もっと有用です。宣言がワークフローにあなたの望みを伝える手段であるなら、その宣言は手の届くところになければなりません。そしてテストが実行できないなら、何かが声に出してそれを告げなければなりません。
