# v6.0.0: 엔지니어링 표준 내장 — AIOS는 코드를 생성할 뿐만 아니라 소프트웨어를 구축한다

> **Quick Answer:** 코딩 에이전트는 "돌아가는" 코드를 생성한다. 그래도 리뷰에서 떨어지는 이유는 매번 같다 — 경계 위반, 얕은 추상, 거짓말하는 이름, 테스트 안전망 부재, 도구 체인 부재. 이것들은 기준의 문제이고, 기준은 아무도 열지 않는 위키 페이지가 아니라 프레임워크에 속한다. v6.0.0은 `aios-engineering-standards`를 출시한다: 고전 서적(Clean Architecture, A Philosophy of Software Design, Clean Code, The Pragmatic Programmer, Refactoring)에서 도출한 하나의 품질 기준을 router가 **어떤 코드 생산 Provider 실행보다 먼저** 로드하고, Definition of Done — 모든 변경이 기존 증거 계약에 더해 통과해야 하는 것 — 을 곁들인다. 문서와 참고 자료(9권 서적 목록, 무료 합법 자료, "서적 원리 → AIOS 메커니즘" 매핑)는 en/zh/ja/ko로 제공된다.

## 실패 모드: 유능한 생성기, 공학되지 않은 산출

워크플로는 이미 올바른 코드를 쓸 수 있었다. 테스트는 돌고, diff는 나오고, 리뷰는 있었다. 그런데 돌아오는 것은 늘 *공학되지 않았다*:

1. **경계 위반.** 비즈니스 로직이 프레임워크, 저장소, UI 세부에 직접 손을 뻗는다. 한 가지 요구 변경이 세 계층을 동시에 깨뜨린다.
2. **얕은 추상.** 전달만 하는 wrapper의 적층. 결코 오지 않을 미래를 위해 예약한 매개변수. 순수한 복잡도, 정보 은닉 제로.
3. **명명과 형태 표류.** 네 가지 일을 하는 함수, 거짓말하는 이름, 열두 곳에서 디코딩되는 오류 코드.
4. **안전망 부재.** 테스트가 없어 모든 리팩터링은 기도이고 모든 리뷰는 영에서 시작한다.
5. **도구 체인 부재.** lint도, pre-commit도, CI도 없다 — 기준은 누군가의 기억 속에 있지 파이프라인 속에 있지 않다.

목록에 **없는** 것에 주목하라: "알고리즘이 틀렸다". 모델 능력은 결코 병목이 아니었다. **기준이** 병목이었다. 그리고 참고 자료의 실행 조언은 기준이 살 곳에 대해 직설적이다: lint, pre-commit 훅, CI를 내장한 즉시 쓸 수 있는 템플릿을 만들어 공학 기준을 자동화 파이프라인으로 만들라 — 문서가 아니라.

## v6.0.0에서 바뀐 것

### 1. `aios-engineering-standards` — 스킬로서의 품질 기준

하나의 스킬. 프레임워크가 로드하고 모든 코드 생산 단계가 공유한다. 고전 서적을 실행 가능한 규칙으로 부호화한다:

- **아키텍처 경계(Clean Architecture).** 소스 의존은 안쪽으로만 향한다. 도메인 로직은 프레임워크, 드라이버, UI 세부를 import하지 않는다. 고응집·저결합·최소 인터페이스. 경계를 정직하게 명명할 수 없다면 설계가 다듬어지지 않은 것이다 — 안개 속을 쓰며 나아가지 말고 설계 옵션으로 돌아간다.
- **깊은 모듈(A Philosophy of Software Design).** 복잡도 = 이해 비용 + 변경 비용. 작은 인터페이스와 깊은 구현이 얇은 전달의 적층을 이긴다. 투기적 범용성을 지운다. 전술보다 전략 프로그래밍: 모든 변경이 코드베이스를 조금 더 좋게 한다.
- **코드 기준(Clean Code / The Pragmatic Programmer).** 이름은 의도를 표현한다. 함수는 한 추상 수준에서 한 가지만 한다. 오류는 반환 코드가 아니라 맥락을 운반한다. DRY = 한 지식에 하나의 권위 표현. 직교성 = 한 변경이 한 곳을 만진다.
- **테스트 기준.** 핵심 로직은 자동 커버리지를 가진다. 리팩터링은 녹색 테스트 뒤에서만. 빌드를 통과시키려고 단언을 약화하지 않는다.
- **도구 체인 기준.** 새 프로젝트·패키지·모듈은 lint, pre-commit 훅, CI, 테스트 프레임워크, 구조화 로깅을 포함해 출하한다 — 기준은 기계가 강제하지 리뷰 기억이 아니다.
- **문서 기준.** 중요한 변경은 짧은 ADD를 기록한다: 결정, 적용 조건, 트레이드오프, 거부된 옵션.

### 2. Router가 코드 생산 Provider보다 먼저 로드한다

`aios-workflow-router`는 선택된 Provider가 `rex-implement`, `rex-refactor-hardening`, `rex-code-review`, `rex-design` 중 하나일 때 본 기준을 **가장 먼저** 로드한다. 완료 문이 확장되었다: 이 단계들은 Provider의 증거 계약**과** 본 기준의 Definition of Done **둘 다**를 요구한다.

이것은 일부러 옆에 볼트로 붙인 새 문이 아니다. "품질 건너뛰기" 경로는 없다 — 기준은 router에 의해 로드되고, 다른 모든 것과 같은 증거 기반 체인 위를 달리며, 각 단계는 여전히 실제 증거 위에서만 풀린다.

### 3. `pre-edit-safety-gate`가 변경 형태를它에 맞춰 대조한다

한 배치의 첫 편집 전에, gate는 이미 변경 형태(로컬 변경 / 확장·재사용 / 리팩터 추출)를 결정한다. 이제 그것을 기준으로도 대조한다: 의존 방향, 깊은 모듈 발견법, 명명, 테스트, 도구 체인. 설계 증거와 품질 증거가 같은 출처에서 온다.

### 4. Definition of Done — 여덟 행, 감각 없음

| # | 항목 | 통과 기준 |
| --- | --- | --- |
| 1 | 행위가 인수 기준을 만족 | 구현 자체 점검이 모두 "예" |
| 2 | 경계 명확 | 올바른 모듈/층. 의존 방향 무손상. 인터페이스 누출 없음 |
| 3 | 모듈이 충분히 깊음 | 새 추상이 실제 세부를 숨김. 얇은 전달도, 예약 매개변수도 없음 |
| 4 | 명명과 함수 | 이름이 실상과 일치. 단일 추상 수준. 오류 처리 통일 |
| 5 | 테스트 커버리지 | 핵심 경로 자동화. 단언 약화 없음 |
| 6 | 도구 체인 | lint / pre-commit / CI / 로깅이 기준 충족 |
| 7 | 문서 | 중요한 변경에 ADD. 계약 갱신 완료 |
| 8 | 증거 | 증거 봉투가 실제 영수증을 인용 |

어느 하나 "아니오"면 계속한다 — 구현 자체 점검과 같은 규율로, 이제 공학 기준이 그 안에 들어 있다.

## 왜 이것이 AIOS를 전통적 에이전트 이상으로 만드는가

전통적인 코딩 에이전트는 코드를 *쓰는* 것을 돕는다. AIOS는 공학 루프를 돌리고, 여러 버전 전부터 돌려 왔다: 계획 전 요구 정렬, 거부된 옵션을 기록하는 설계 결정, 시나리오 영수증이 있는 행위 보존 경화, Fowler 악취 기준선과 fixed-point diff에 대한 리뷰 — 각 단계는 타입화된 증거 위에서만 풀린다.

v6.0.0은 마지막 틈을 메웠다: **"좋다"는 것의 의미가 더 이상 희망이 아니라 프레임워크 1급 시민이다.** 에이전트가 당신의 스타일 가이드를 기억할 필요는 없다 — router가 한 줄 쓰기 전에 기준을 건네고, 완료 문이 결과를 기준으로 검사한다. 이것이 코드 생성기와 소프트웨어 공학 시스템의 차이다.

## 업그레이드

`aios update`(또는 `aios init --all`)를 실행해 새 스킬을 각 클라이언트의 스킬 루트로 투사하고 클라이언트를 재시작한다. 기준은 다음 코드 생산 작업에서 자동으로 로드된다 — 설정도, 우회도 필요 없다.
