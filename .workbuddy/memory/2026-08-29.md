## 修复：计划任务状态回写越级（Harness/CTX/Rex 控制面）

用户报告 v5.8.0/v5.8.1 存在「尚未执行的 pending 任务被标成 done」的缺陷。

根因：`scripts/lib/planning/plan-runtime.mjs` 的 `syncPlanWithIterationOutcome` 每轮都用
`findWritableTask()` 重新挑任务（in_progress → 否则第一个 pending），而不是绑定 provider
明确返回的任务 ID。外层 `solo-runtime/loop.mjs` 与内部 `subagent/phase finalize`
（`phase-plan-sync.mjs`）两条路径对同一个成功 turn 各触发一次同步时，第二次就会越级标 done。

改动：
- `syncPlanWithIterationOutcome` 新增 `taskId` 入参，并读 `outcome.taskId`
- `normalizeSoloIterationOutcome` 保留 `taskId` 字段（此前会丢弃）
- `loop.mjs` 用 `markPlanTaskInProgress()` 返回值里的 task.id 回传
- 无显式 taskId → 只落证据、绝不标 done
- 写 done 前校验证据：outcome 需带 evidence/keyChanges/summary；任务 `targets` 需在
  `git diff --name-only` 中有实际改动
- `attachPlanVerificationEvidence` 质量门通过只结算 in_progress 任务，不 fallback pending

## 关键事实：WorkBuddy **有** CLI（我一开始判断错了）

`/Applications/WorkBuddy.app/Contents/Resources/app.asar.unpacked/cli/bin/codebuddy`
（别名 `cbc`，v2.115.0，package 名 `@genie/agent-cli`）。

我最初用 `which workbuddy` 判"无 CLI"是错的 —— 真实二进制叫 **codebuddy**，
且默认不在 PATH。能力齐全：`-p/--print` 非交互、`--output-format json|stream-json`、
`--model`、`--worktree`、`--acp`（stdio/ndjson）、`-y/--dangerously-skip-permissions`、
`--json-schema`、`--max-turns`、`--serve`（HTTP）。

实测可当 provider：
`codebuddy -p "<prompt>" --dangerously-skip-permissions` → exitCode 0、stdout `OK`。

**教训**：判断"某客户端有没有 CLI"不能只靠 `which <产品名>`，
要看应用包内有没有 cli/bin（尤其 macOS .app）。

### commandName 必须是 codebuddy，不能填 workbuddy

`commandName` 同时决定三件事：shim 文件名（`~/.aios/bin/<commandName>`）、
PATH 检测（`checkSoloHarnessProfileReadiness`）、shim 内 `--command` 的真实命令名。
填成产品名会让整条链静默断裂（shim 去找不存在的 `workbuddy`）。

### 让 workbuddy 当 provider 要改四处

1. `definitions.mjs`：commandName / modelArgFlag / unattendedArgs / capabilities(+harness)
2. `ctx-agent-core/one-shot.mjs` 的 `ONE_SHOT_HANDLERS` 加 `workbuddy-agent`
3. `ctx-agent-core/interactive.mjs` 的 `INTERACTIVE_BUILDERS` 加 `workbuddy-agent`
4. 用户侧：把 app 的 `cli/bin` 加进 PATH

**修正（15:30 复查）**：`~/.aios/bin/workbuddy` 经复查是**合法的 AIOS native shim**
（`AIOS_NATIVE_SHIM managed`，路由到 `contextdb-shell-bridge.mjs`，`--command 'workbuddy'`
用的是客户端定义 key，正确）——**不是孤儿，保留勿删**。删了会破坏 workbuddy 的原生 shell 拦截。
（此前"可以删"的判断是基于错误假设，已推翻。）

## 回归修复：sync 内部的 `markPlanTaskInProgress` 仍会造成「越级」in_progress（15:30）

上一轮对 `syncPlanWithIterationOutcome` 的修复只堵了"标 done"的越级，但 sync 内部仍**无条件**
调用 `markPlanTaskInProgress`。`subagent-runtime/phase-plan-sync.mjs` 以**无 taskId** 的
`{outcome:'success', ok:true}` 调用 sync 时，会把下一个 pending 任务强制置为 `in_progress`
（虽不标 done，但错误推进了计划状态）。这是 review 子代理（被 429 阻断）要抓的回归点。

修复（自我复查替代子代理，因 rate limit 未清）：
- `syncPlanWithIterationOutcome` 内**移除** `markPlanTaskInProgress` 调用 —— sync 只记录证据 +
  处理显式 taskId，绝不再改动 `in_progress`（该状态完全归 `solo-runtime/loop.mjs` 持有）。
- 删除死代码 `hasCommitEvidence`（grep 全仓无引用）。
- `hasTargetFileChanges` 修正绝对/相对路径匹配（绝对路径先转 `path.relative` 再比对，
  原 `names.includes(target)` 对绝对路径恒为 false）。

验证：`node --test scripts/tests/plan-runtime.test.mjs` 5/5 通过；
`npm run test:regression` 1064 tests / 1054 pass / 0 fail / 10 skipped（与基线一致）。
