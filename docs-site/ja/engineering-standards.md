# エンジニアリング基準

## Quick Answer（ひとこと回答）

従来のコーディングエージェントは「動く」コードを生成する。AIOS が生成するのは**工学された**コードだ。v6.0.0 以降、ワークフローのすべてのコード生産ステップは同じ品質基準——`aios-engineering-standards` スキル——を先に読み込む：『Clean Architecture』のアーキテクチャ境界、『A Philosophy of Software Design』の深いモジュール、『Clean Code』の命名と関数のルール、『The Pragmatic Programmer』の DRY と直交性。そして Definition of Done を通過するまで完了とは見なされない。この基準は既存の証拠駆動能力チェーンに乗るもので、迂回できる追加の門ではない。本ページが公開基準であり、参考資料（四段階能力モデル、九冊の書単、無料で合法なリソース）を併載する。

## なぜ：生成コードの品質ギャップ

生成コードがレビューを落ちる原因は予測可能で、しかも「アルゴリズムが間違っている」ことはほとんどない：

- **境界違反**——ビジネスロジックがフレームワーク、ストレージ、UI の詳細に直接手を伸ばすので、1 つの要件変更が三層を同時に壊す。
- **浅い抽象**——転送するだけの wrapper の積層、決して来ない未来のために予約されたパラメータ：情報隠蔽ゼロの純粋な複雑さ。
- **命名と形の漂流**——一つの関数が四つのことをする、嘘をつく名前、十二か所で判定されるエラーコード。
- **安全網の欠如**——テストがないので、リファクタリングはすべて祈祷で、レビューは毎回ゼロから。
- **ツールチェーンの欠如**——lint も pre-commit も CI もない：基準は誰かの記憶の中にあり、パイプラインの中にない。

これらはモデルサイズの問題ではない。**基準の問題**だ。そして基準は、誰も開かない wiki ページではなく、フレームワークワークに属する。

## AIOS がすでに持っていて、従来のエージェントにないもの

AIOS はローカルファーストのオーケストレーションコントロールプレーンであり、コード生成器を包むチャット殻ではない。ソフトウェア工学能力はここではすでに構造的で——v6.0.0 が品質の半分を明示的なものにした：

| 従来のコーディングエージェント | AIOS |
| --- | --- |
| diff を生成して祈る | 各ステージが型付き証拠（`implementation-diff-recorded`、`focused-tests-pass`、receipt）を出してから次のステージが解放される |
| 「完了」はモデルがそう言ったこと | 完了 = Definition of Done チェックリストと証拠契約の両方を通過 |
| 基準は誰も読み込まないスタイルガイドの中 | 基準はスキルであり、router がコード生産 Provider の実行**前**に読み込む |
| レビューは感覚 | レビューは fixed-point diff に対し Fowler スメル基線＋仕様軸＋基準軸で走る |
| 品質は最後の磨き | 品質門は 計画 → 実装 → 硬化 → レビュー の全鎖に組み込まれている |

要するに：従来のエージェントはコードを*書く*のを助ける。AIOS は工学ループを回す——要件整合、却下オプションを記録する設計決定、行動保存の硬化、証拠付きレビュー——そして今や、書かれるすべてのものの共通品質基準。

## 品質基準

### 1. アーキテクチャ境界（Clean Architecture）

- **依存ルール**：ソース依存は内側にのみ向かう。ドメインロジックはフレームワーク、ドライバ、UI の詳細を import しない。外側の層はドメインが定義するインターフェースを通じて依存する。
- **高凝集・低結合**：一緒に変わるものを一つのモジュールに集める。一つのモジュールは一つの理由でしか変わらない。
- **最小インターフェース**：モジュールは詳細を最小で誠実なインターフェースの裏に隠す。インターフェースにフレームワーク型、ストレージ構造、サードパーティ DTO が現れたら境界漏洩。
- **命名が境界のテスト**：モジュールや境界を誠実に命名できないなら、設計は考え切れていない——霧の中を書き進めるのではなく、設計オプションに戻る。

### 2. 深いモジュール（A Philosophy of Software Design）

- 複雑さ＝理解コスト＋変更コスト。新しい抽象はすべてこの和で測る。
- **深いモジュールを優先**：小さなインターフェースと、大きく隠された実装は、薄い転送の積層より優れる。
- **浅いモジュールを疑う**：実装と同じ大きさのインターフェース、情報隠蔽を増やさない wrapper、投機的な未来のために予約されたパラメータ——削除する。
- **戦術的プログラミングより戦略的プログラミング**：すべての変更でコードベースを少し良くする（ボーイスカウト規則）。速い納品と構造改善は二択ではない。
- **コメントは設計ツール**：明確なコメントが書けないなら、境界か責務が曖昧だ——まず設計を直す。コメントは「なぜ」を説明し、「何を」のナレーションではない。

### 3. コード基準（Clean Code / The Pragmatic Programmer）

- 名前は意図を表す。理由づける前に改名する。一つの関数は一つの抽象レベルで一つのことだけをする。
- エラーはコンテキストを伴う例外かエラー型で表現する。呼び出し側が毎回デコードする戻りコードは使わない。
- DRY：一つの知識には一つの権威ある表現だけがある。二つの似たブロックは、それが**同じ**知識のときだけ統合する——偶然の相似は誤った結合より安い。
- 直交性：一つの要件変更は一か所を触る。頭の中の diff が五ファイルあるなら、それは構造のシグナルであり、運が悪いのではない。

### 4. テスト基準

- コアロジックは自動カバレッジを持つ（ユニット＋必要に応じ統合）。リファクタリングと硬化は緑のテストの後でのみ行う。
- ビルドを通すために断言を弱めたり、ケースを削除したり、スイートをスキップしたりしない。テストは「振る舞いが変わっていない」証拠だ——テストなしのリファクタリングは祈祷である。

### 5. ツールチェーン基準（基準の自動化）

> 機械が検査できるルールは、人のレビュー記憶に頼るべきではない。——参考資料の落地アドバイス：lint、pre-commit フック、CI を内蔵した、開けば使えるテンプレートを届けて、工学基準を自動化パイプラインに変える。

新しいプロジェクト・パッケージ・モジュールには以下が必須：

- [ ] リポジトリの既存基準と一致した lint / フォーマット設定
- [ ] pre-commit フック（lint＋高速テスト）
- [ ] CI 設定（lint＋静的検査＋全テスト）
- [ ] テストフレームワークと、少なくとも一本の実行可能なコアパステスト
- [ ] 構造化・レベル付き・検索可能なロギング——裸の print ではない

既存リポジトリはまず自分自身の記録された基準に従う。ギャップは納品ノートに記録され、黙って無視も、私的な平行規範を押し付けることもない。

### 6. ドキュメント基準

- 重要な変更——境界、インターフェース、データ構造、運用方式に触れるもの——は短い ADD を記録する：決定、適用条件、トレードオフ、却下されたオプション。設計スキルの決定記録と同じ形で、実施計画に膨らませない。
- API・公開インターフェースの契約は変更とともに更新される。「知識が誰かの頭の中にしかない」は未完了と見なす。

## Definition of Done

「完了」と言うには全行が必要。どれかが「いいえ」なら作業を続ける：

| # | 項目 | 合格基準 |
| --- | --- | --- |
| 1 | 振る舞いが受け入れ基準を満たす | 実装セルフチェック表がすべて「はい」 |
| 2 | 境界が明確 | 変更は正しいモジュール/層にある。依存方向は無傷。インターフェース漏洩なし |
| 3 | モジュールが十分深い | 新しい抽象は実のある詳細を隠す。薄い転送も予約パラメータもない |
| 4 | 命名と関数 | 名前が実態と一致。単一抽象レベル。エラー処理が統一 |
| 5 | テストカバレッジ | コアパスが自動化。断言は弱められていない |
| 6 | ツールチェーン | lint / pre-commit / CI / ログが第 5 節の基準を満たす |
| 7 | ドキュメント | 重要な変更に ADD。インターフェース契約を更新済み |
| 8 | 証拠 | 証拠信封が実回執（テスト、diff、シナリオ）を引用 |

## ワークフローへの乗り方

```text
router（aios-workflow-router）
  └─ コード生産 Provider を選択（rex-implement / rex-refactor-hardening / rex-code-review / rex-design）
       └─ aios-engineering-standards を最初に読み込む  ← 共通品質基準
            └─ Provider が自分の証拠駆動ステップを実行
                 └─ 完了 = Provider の証拠契約 かつ 本 Definition of Done の両方を通過
```

`pre-edit-safety-gate` はさらに最初の編集前に、選んだ変更の形（ローカル変更／拡張・再利用／リファクタ抽出）をこの基準で照合する。どのステージも opt out できない——「品質スキップ」ルートは存在しない。基準は丁寧さではなく router によって読み込まれるからだ。

## 参考資料

### 工学能力の四段階モデル

参考会話は工学の成長を四段階で説明し、AIOS はそのすべてに対応する：

1. **単兵能力の奠定——コード品質とリファクタリング**：言語范式と lint 規範の遵守、KISS / DRY、ボーイスカウト規則、リファクタリングに保険をかけるユニット・統合テスト。
2. **システム思考の進化——設計パターンとモジュール分割**：SOLID、高凝集・低結合、最小インターフェース、詳細の対内封装。
3. **工学自動化の構築——CI/CD と品質治理**：Conventional Commits、Gitflow / Feature Branch、毎回の commit や PR で lint・静的検査・テストを自動実行。構造化ログとメトリクス監視。
4. **複雑さの掌握——プロジェクト管理と納品控制**：大きな要件を独立納品可能な MVP に分解しリスクバッファを確保。ADD、API ドキュメント、要件追跡マトリクスで、知識が誰かの頭の中にしかない状態を避ける。
