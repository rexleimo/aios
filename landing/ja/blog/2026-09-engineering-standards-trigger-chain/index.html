v6.2.0：実際にトリガーされるエンジニアリング標準

AIOS は以前からエンジニアリング標準スキルを同梱していました——しかし一度もトリガーされたことがありませんでした。「配布されたが名指されない」監査、新しい共有参照プロジェクション経路、ファイル粒度ベースラインにより、古典的なソフトウェア工学の規律がコードを生成するすべての経路に適用されるようになりました。

← 全部文章 · 首页

疑いはありましたが、実態はもっとひどかった：AIOS は rex-engineering-standards スキル——Clean Architecture の境界、深いモジュール、 命名、Definition of Done——をずっと同梱していたのに、一度もトリガーされて いなかったのです。内容が間違っていたのではなく、消費すべき側がどこからも名指していなかったのが理由です。

監査結果

ファイルを実装に入れる問題は 0.7.0 で解決済みでした：この標準は以前 マシンごとの ~/.zcode/skills/ コピーにのみ存在し、バージョン管理外で、他 クライアントへ投影されず、再インストールで消えていました。現在は投影される スキルツリーの中にあります。監査が見たのは、その修正後も残っていたものです。

二つの切断点が残っており、それぞれ単独で十分でした：

  1. 配布されたが、名指されなかった。 install.mjs はこれを投影し、 client-install.test.mjs はこれを数えます——つまりファイルはすべての クライアントのディスク上にありました。しかし出荷物の内部では、誰もそれを 読むよう指示していませんでした：コード生産 Provider 四つはいずれも名指さず、 AGENTS.md も言及なし。存在した参照者は aios-workflow-router と pre-edit-safety-gate のみ——どちらも AIOS ホスト側の案内であり、rex-harness を 単独で使うクライアントは読み込みません。ファイルは全員に配られたのにどの シーケンスにも要求されませんでした。標準は「実装前に私を読め」と主張していましたが、実装側の スキルはその存在を知りません。スキルの読み込みは呼び出しごとのプル型であり、 名指しされないものは誰にも引かれません。
  2. ランタイムの安全網がない。 ファイル粒度——ユーザーが最も痛感する 項目——は機械検査が最も容易なルールなのに、何も検査していませんでした。 「名指されているか」自体も検査対象でなかったため、この切断点は肉眼では 見えませんでした。

結果は予想通り：コードにエンジニアリングの形がありません。ファイル名は 不明瞭、一つのファイルに大量の責務が山積み。

修正：三つ目のスキル種別

Rex スキルには二種類ありました：rex-workflow エントリと、Provider——Rex Command が選択して進められる Capability です。この標準はどちらでもない： Provider になるべきではない（capability 契約がない）が、プロジェクションと 共に配布される必要がある。そこでインストーラーに第三の経路ができました：

  • rex-harness/src/clients/install.mjs に sharedReferenceSkillIds を追加—— Provider と同じく全クライアントに投影されるが、Command には決して選択され ない。スキル自体の契約（「Provider の流程ではなく、事前標準」）は誠実な まま保たれます。
  • コード生成系 Provider——rex-implement、rex-design、rex-code-review、 rex-refactor-hardening——には明示的な前置ステップが付きました：まず標準を 読み、その Definition of Done を各ゲートと共に確認する。
  • AGENTS.md にこのルールを記録したので、全クライアントがセッション開始時に 目にします。

補われたベースライン：ファイル粒度

旧標準は関数とモジュールをカバーしましたが、ユーザーが最も訴える単位を 飛ばしていました。新しい §4 がそれを補います：

  • 一ファイル一責務。 ファイル名が中身を説明できない = 責務が不明瞭—— 書く前に分割するか改名する。
  • 約 400 行のソフト上限。 上限に近づいたら責務境界を越えていないか自問。 超える場合は、なお単一責務である理由を納品説明に記す（generated・ テーブル駆動・純データファイルは除く）。
  • 命名はリポジトリに従う（kebab-case のアクションモジュール、index.ts エントリ）。a_v2、a_final、a_utils のような無意味な分割は禁止。

Definition of Done の 5 行目に加わったため、rex-implement の self-check gate は「一つの巨大ファイル」的な納品を fail-closed で落とします。

繰り返し学ぶあの教訓

今効いた修正は「スキルをもっと上手に書く」ではなく「スキルを参照され、 投影され、検査可能にする」でした——競合分析が別の方向から繰り返し導くのと 同じ結論です：成熟したハーネスで「起きるべきか」をプロンプト層に留めている ものはありません。プロンプトの中だけに生きる標準は提案にすぎません。 消費側に名指しされた標準だけがゲートです。配布は欠けていたピースではありません でした——ファイルはもともと全クライアントのディスク上にあり、それでも一度も 発火しませんでした。

今回のリリースのもう一つ：ホストは未公開のカーネルを同梱できない

同じ監査は一段上の、より悪い形も暴きました。公開済み v6.1.0 のアーカイブは rex-harness のワークツリーを同梱しますが、そこに含まれていた rex-harness バージョン にはサブモジュール remote 上の tag もリリース成果物もありませんでした。何も失敗し なかったのは、何も検査していなかったからです——ホストの changelog はどこにも解決 できないカーネルバージョンを引用し、rex-harness を単独で使う人はそれを受け取れて いませんでした。

いま scripts/check-release-submodule.mjs が記録された gitlink がサブモジュール remote の tag に指されていることを証明し、tag が無い／証明できない場合は release-preflight.sh がホストリリースを切りません。公開順序は慣習ではなく ゲートです：まずサブモジュール、次にホスト。

検証：rex-harness 215 テスト、client-install と skill-sources スイート、 scripts 側プロジェクションスイートすべて合格；プロジェクション対象スキルすべての canonical digest を projection-history.json に append-only で登記済み（0.7.0 の digest も残す——それでなくとも 0.7.0 を使うクライアントが更新できるため）、 ローカル投影を更新し、rex-harness doctor はエラー ゼロ。

そして静かな回归を防ぐガードを追加：skill-sources.test.mjs は、コード生成系 Provider のいずれかがこの標準を名指しやめた瞬間にビルドを落とします。 「誰も参照しないスキル」はランタイムでは見えない欠陥なので、検査は客観的事実 （出荷済みツリーに文字列が存在するか）に限定し、レビュー意見にはしません。
