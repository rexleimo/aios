TL;DR: 이번 릴리스의 주제는 "추측하지 않기"입니다. 계획 원장은 같은 작업 항목을 이중 등록하면 조용히 두 문서로 갈라질 수 있었고, 능력 활성화를 가진 쪽은 하나뿐이었습니다. aios plan은 쓰기 요청에 읽기 전용 뷰를 건네고 exit 0으로 끝냈습니다. 선언된 검사(디렉터리 예산, 스킬 변경의 영향 테스트 선택)는 디스크에는 있지만 CI에서는 한 번도 돌지 않았습니다. v6.4.0은 각 계열을 못박습니다. A21은 계획 턴이 활성 원장을 재사용하게 하고, A22는 작업 항목에 정규 아이덴티티를 부여하며, A23은 그 아이덴티티를 Capability Command 바인딩까지 전파합니다. A19는 미구현 서브커맨드를 status로 치환하는 대신 거절하고, A20은 트레이닝 게이트가 검증 베이스와 각 거절의 구제책을 말하게 합니다. 같은 릴리스에서 ADR 0003의 착지 세 질문에 따라 mattpocock/skills v1.3 트리오를 양면으로 채택했습니다. 부모 저장소에는 retro와 implement-spec이 더해지고, rex-harness 0.11.0은 스탠드얼론용 오케스트레이션 스킬 rex-implement-spec / rex-pr / rex-retro를 출시합니다. 설치 프로젝션은 14에서 17로 늘어납니다.

원장은 갈라지지 않는다 (A21 → A22 → A23)

이 축은 같은 병소의 세 번 발현을 고칩니다. 계획 원장은 "어떤 문서가 활성인가"로 답하며, 같은 작업 항목을 이중 등록하면 둘을 만들 수 있었다.

A21이 먼저 재사용을 고칩니다. workflow-policy.mjs는 "계획 턴은 항상 새 원장을 만든다"고 하드코딩하고 있었고, 같은 항목을 두 번 등록하면(plan start 후 plan auto-gate) -2 접미사만 다른 두 문서가 생기고 능력 활성화를 가진 쪽은 새것뿐이었습니다. 활성 계획에 작용하는 plan task와 plan add-evidence는 첫 원장을 조용히 고아로 만들었습니다. 재사용은 이제 상태 사실(활성이며 종결되지 않은 계획이 존재)로 키되고, 목적 텍스트 유사성으로는 절대 키되지 않습니다. 선언된 탈출구는 plan auto-gate --new-work-item이며, strict 모드도 재사용합니다. strict란 "항상 원장에서 일한다"이지 "매 턴 하나씩 주조한다"가 아니기 때문입니다.

A22가 아이덴티티를 더합니다. plan start --work-item <id>는 작업 항목에 정규 아이덴티티를 부여합니다(대소문자/공백/구두점 정규화, ..·경로 구분자·제어 문자 거절). 아이덴티티는 선언되지, 절대 추론되지 않습니다. 기존 id는 그 원장을 재활성화하고, 스토어를 잃어도 문서가 살아 있으면 재입양(recovered: true)합니다. 다른 -2를 주조하는 대신. 가드는 우리가 예상하지 못한 구멍을 잡았습니다. 선언했지만 값이 빈 --work-item ""는 "플래그 부재"로 접혀 무키 경로로 떨어져 이 기능이 막기 위해 존재하는 형제 원장을 정확히 주조했습니다. 아이덴티티는 이제 존재성으로 판정되고 빈 선언은 거절됩니다.

A23이 전파를 닫습니다. A22가 plan start에 아이덴티티를 줬어도, 계획 턴의 원장을 쓰는 게이트는 여전히 아무것도 넘기지 않았습니다. 게이트가 주조한 원장은 workItemId: ''인 채였고 rex 활성화는 경로나 턴별 해시로 키되어 있었습니다. 원장은 어떤 id에 답하고, 완료를 인정하는 Command는 다른 것에 답하고 있었던 것입니다. 활성화 키는 이제 순서 있는 선호입니다. 선언 id → 원장 경로 → 턴 해시, id→경로 읽어통이 포함되어 A23 이전의 경로 키 방식도 여전히 도달 가능합니다. 두 우선 규칙은 설계가 아니라 실측에서 나왔습니다. 선언 id의 정규형이 활성 계획의 id와 다르면 자체 원장을 만든다(A21의 재사용은 명시적으로 다른 선언을 삼켜서는 안 된다). --work-item X --new-work-item은 우선순위로 해결하는 대신 exit 1로 거절된다. 이 조합은 활성화 키가 충돌하는 두 번째 원장을 쓰기 때문입니다. 직관에 반하는 못 하나. canonicalizeWorkItemId('')는 ''을 반환해야 합니다. 공유 slugify는 빈 입력에 리터럴 'plan'으로 폴백하고, 그것이 선언 없는 모든 턴을 "다른 작업 항목"처럼 보이게 해 A21의 재사용을 조용히 꺼버렸기 때문입니다(원인을 찾기 전까지 5개 테스트가 실패했습니다).

거절은 기능이다 (A19)

aios plan은 두 가지 조용한 치환으로 원장을 쓸 수 없게 만들었습니다. argv 파서는 모든 미구현 서브커맨드를 status로 재작성했고(그래서 plan list도, 오타난 plan setstatus도, 계획을 출력하고 exit 0), status 브랜치는 --status/--note/--force를 무시했습니다(그래서 plan status --status done은 아무것도 바꾸지 않고 exit 0). 2026-09-21에 끝난 작업 항목이 그래서 3주간 executing에 갇혀 있었습니다. 그리고 낡은 executing 계획이야말로 모든 「계속」 재개가 신뢰하는 것입니다. 원장은 다음 세션을 능동적으로 오도하고 있었습니다.

수정은 fail-closed로 갑니다. 파서는 선언된 서브커맨드를 그대로 통과시키고 어휘 사본을 소유하는 것을 멈춥니다. 브랜치 집합을 소유한 ops 레이어가 PLAN_SUBCOMMANDS를 내보내고 미구현 이름을 유효한 목록과 함께 거절합니다. status는 쓰기 플래그를 거절하고 plan set-status를 가리킵니다. 헬프는 마침내 aios plan set-status …를 알립니다. 이 줄의 부재야말로 함정이 살아남은 이유입니다. 두 변이는 독립적으로 잡힙니다. 파서 폴백의 재도입은 C2만 실패시키고, status 가드의 삭제는 C3만 실패시킵니다.

게이트는 선언된 곳에서 돈다 (A20 + 디렉터리 예산 + 영향 테스트)

A20 — 트레이닝 게이트가 검증 베이스를 말한다. verify-training은 아홉 가지 실패를 한 문장으로 압축했기 때문에, 잘못된 베이스에서 기록된 인증서가 낡은 콘텐츠와 똑같이 보였습니다. 그런데 구제책은 다릅니다. 거절된 각 항목은 이제 code + reasonKind + remedy(정확한 명령)를 실으며, 변조된 베이스라인 아티팩트와 다른 베이스에서 기록된 인증서는 두 브랜치로 갈라지고, PowerShell 측 프리플라이트는 실패 시 출력을 삼키는 대신 다시 흘려보냅니다.

디렉터리 예산 — 규칙이 CI에서 도는다. AGENTS.md는 "디렉터리당 최대 8 항목"을 선언하고, check-dir-budget.mjs는 차단 위반에서 실제로 exit 1 합니다. 그러나 실행면이 0이었습니다. package.json에도, 워크플로에도, pre-commit에도 없었고, 저장소는 차단 위반 2개로 표류하는 동안 모든 스위트는 초록이었습니다. 이제 pretest:scripts의 두 번째 단계로 돕니다. CI(및 릴리스)는 새 초과 디렉터리에서 실패합니다. 표류한 두 디렉터리는 먼저 스크립트의 래칫 베이스라인에 동결되고, 의미적 분할은 별도 항목입니다.

영향 테스트 — 스킬 변경이 조용히 0개 테스트를 선택하지 않는다. 이번 사이클 실측: skill-sources/retro/SKILL.md를 포함한 8파일 변경에서 셀렉터는 "선택 0/219"를 출력했습니다. skill-sources 파일은 가드 스위트가 디렉터리 순회로 읽고 import로는 절대 읽히지 않아 정적 영향 그래프에 변이 없었던 것입니다. 이제 모든 skill-sources/ 변경은 스킬 가드 접두사로 귀속되어 13개 가드 테스트가 선택됩니다.

세션에서 환경으로의 루프 (트리오 양면 + A16)

이 릴리스는 한 질문에도 답합니다. 회고에서 나온 환경 교훈은 어디에 착지하는가.

부모 저장소는 ADR 0003의 착지 세 질문에 따라 mattpocock/skills v1.3의 retro와 implement-spec을 채택합니다. retro는 세션을 "코드가 아니라 환경을 바꾸라"는 후보에 대해 일곱 범주(내비게이션 포인터, 결정론적 검사, 코딩 표준, AGENTS.md 추가/삭제, 도구 경제성, 무효한 지시, 정보 도달성)로 돌아봅니다. 제안만 하고 파일 쓰기는 절대 없으며, 모든 후보에 출처 참조가 필수이고, 일곱 범주 각각이 "미확인"을 accounting합니다. implement-spec은 이미 수용 기준과 작업 항목 그래프를 갖춘 spec의 실행 진입입니다. 프론티어를 잡고, 승인된 aios work 게이트를 통해 병렬 디스패치하고, 통합 브랜치에서 닫고, /review로 마무리합니다.

스탠드얼론 rex-harness 사용자는 둘 다 없으므로, rex-harness 0.11.0은 framework-free 오케스트레이션 스킬 rex-implement-spec / rex-pr / rex-retro를 출시합니다. Provider가 아니고 Capability Command에 선택되지도 않으며, rex-workflow와 같은 오케스트레이션 면을 공유합니다. 스탠드얼론 설치 프로젝션은 14에서 17로. 양면 배치는 grill ↔ rex-requirements와 같은 선행 사례를 따릅니다.

마지막으로 오퍼레이터 승인의 청소입니다. 저장소 전체에서 임포터가 0인 "핵심 인프라 배럴"을 자칭하던 src/core/index.mjs가 삭제되었습니다(등록 A16 종결). 헤더가 그리는 엔트리 포인트로 채택하는 것은 기능적 이득 없는 저장소 전체 import 경로 재작성을 의미합니다. 필요할 때 다시 세우는 편이 데드 코드를 유지하는 것보다 쌉니다.

업그레이드 노트

  • 파괴적인 마이그레이션은 없습니다. 갱신 후 aios init을 재실행(또는 스킬 재동기화)하면 새 retro / implement-spec 스킬이 생깁니다.
  • rex-harness 포인터는 0.11.0으로 전진합니다. 스탠드얼론 전용 사용자는 프로젝션되는 오케스트레이션 스킬이 3개 늘지만 기존 동작 변화는 없습니다.
  • 이번 릴리스의 트레이닝 증거는 v6.3.0 베이스로 재발행되었습니다(결정론적·로컬·모델 미개입). 워크스페이스에 자체 스킬 변경이 있다면 태깅 전에 같은 구제를 실행하세요. aios skill certify --changed --base v6.3.0.
