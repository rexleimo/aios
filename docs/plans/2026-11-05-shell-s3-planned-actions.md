# S3 计划：把「接入矩阵」从只读报表做成可操作的产品面

触发：用户实测 `npm run app` 后反馈——「既不能操作，又不能编辑」「你现在只是想表达可以打出这样一个 box 吧」。
结论：M1 按 ADR 决策 2 交付的是**只读状态板**，它不是产品；壳（S1/S2）已经把承载它的车造好了，缺的是车里的东西。

## 现状与差距（逐条对应截图观察）

| 现象 | 事实 | 差距 |
|---|---|---|
| 13 行 × 7 轴的表格铺满窗口，右侧被裁切 | 表格没有最大宽度，也没有横向容器 | 布局没有信息层次 |
| 每行重复一条蓝色「限制与证据（x/7 轴）」 | 13 次同样的入口，等于没有入口 | 不构成可发现的操作面 |
| 「当前阻断」是 4 条英文原文 | 只陈述现状，不说怎么修 | 没有闭环 |
| 单元格只有「有/无」方块 | 配置里只有行级 `limits[]`，逐轴原因不存在（实测） | 表格的表达已到顶，无法再挖 |
| 没有任何可点执行的东西 | 页面只有一个取数通道 `data/load.mjs` | 无动作、无编辑 |

## 「做完」的定义（四条，缺一条就不算）

1. **可操作**：逐客户端与逐阻断项都有动作，动作由**服务端**执行（ADR 决策 3），输出流式回显，结束后结果回写页面。
2. **可编辑**：`config/host-capabilities.json` 的能力轴/目标等级/limits 可在界面上改，保存前显示 diff、保存后跑校验，失败可回滚。
3. **可诊断**：每条阻断能展开「为什么 + 怎么修 + 一键执行」，执行完必须重新采集并显示变化（不是重载页面假装成功）。
4. **视觉重做**：不再是一张铺满的表格；有最大宽度、层次、可筛选；同一入口只出现一次。

## 动作清单（按 CLI 已有能力，不新造语义）

| 动作 | 命令 | 性质 | 实测耗时 |
|---|---|---|---|
| 重新采集状态 | `aios status --json` | 只读 | 秒级 |
| 技能健康 | `aios skill health --json` | 只读 | 0.25s |
| 仓库体检 | `aios doctor` | 只读 | ~14s（需要流式回显） |
| 安装/修复某客户端 | `aios setup`（按需带 client） | 写主目录，需确认 | 分钟级 |
| 安装外部技能 | `aios skill add <source> --client <c> --yes --json` | 写主目录，需确认 | 分钟级 |
| 编辑能力声明 | 写 `config/host-capabilities.json` | 写仓库，需 diff + 校验 | 即时 |

**动作执行的唯一形态**：`POST /api/actions/<id>`（Node 运行时，固定 argv，不接受用户拼接的字符串），
`text/event-stream` 回显 stdout/stderr，最后一条事件带退出码与结构化结果。
动作 id → argv 的映射是白名单，是安全边界；界面只能选 id，不能传命令。

## 两个视觉方向（需用户选一个再动 UI）

**A. 控制台（Console，推荐）**：左侧 13 行客户端列表（状态灯 + 证据覆盖 + 阻断标记），右侧详情：
已声明轴、`limits` 原文、证据、动作按钮与执行输出。顶部一条全局状态条（声明/覆盖/阻断/未覆盖 + 重新采集）。
理由：用户的抱怨是「不能操作」，控制台把「选一个对象 → 做一件事 → 看结果」做成主循环。

**B. 仪表盘（Dashboard）**：上方 4 个指标卡，中间保留矩阵但可筛选/排序，点单元格开右侧抽屉放详情与动作。
理由：更像产品主页，适合汇报与概览；但「操作」仍然是第二层的抽屉。

两者共用同一套 `--rex-*` token 与 DESIGN.md 的视觉语言；差别在信息结构，不在配色。

## 顺序

1. 动作层 API（与视觉无关，先做）：白名单 + SSE + 结果事件 + 测试。
2. 按选定方向重做页面结构。
3. 编辑写回（diff → 校验 → 回滚）。
4. 端到端验证：真命令、真输出、真回写。

**不做**：插件 marketplace、实时路由图（二期）、签名/自动更新。

## 信息架构：为什么 magpie 有 8 组导航，我们只有 1 页

参照物是 magpie（用户给的截图）。它能长出「使用 / 模型 / 观测 / 扩展 / 设置」五组导航，
原因不是界面做得好，而是它**站在请求路径上**（底部状态条写的网关地址 `127.0.0.1:3425`）：
会话、用量、路由、供应商、插件的数据都来自它自己转发的每一个请求。

ADR 0007 把网关与请求级路由放在**二期**，一期只做有现成数据的接入矩阵。所以差的不是界面，
是数据面：我们只交付了 1 个页面，因为一期只有那一个数据源。

AIOS 自己的数据面（实测，命令均可出 JSON）：

| 导航 | 页面 | 数据源 | 状态 |
|---|---|---|---|
| 使用 | 总览 | `aios status --json` + `config/host-capabilities.json` | 已有 |
| 使用 | 会话 | ContextDB 会话表 | **缺查询接口**（库在手，需要一层只读查询） |
| 使用 | 记忆 | `aios memory report --json`、memo | 可直接接 |
| 模型 | 用量 | `aios tokens report --json` | 可直接接（按层记账，不是请求级） |
| 模型 | 供应商 / 路由 / 网关 | `model-availability.json` + 路由选择 | **二期**：请求面未建 |
| 观测 | 接入矩阵 | 现有 | 已有 |
| 观测 | 技能健康 | `aios skill health --json` | 可直接接 |
| 观测 | 团队 / 工作流 | `aios agents list --json`、`aios workflow list --json` | 可直接接 |
| 扩展 | 集成 | `aios integration list --json` | 可直接接 |
| 扩展 | 技能 | `aios skill add/health` | 可直接接 |
| 设置 | 能力声明编辑 | `config/host-capabilities.json` 写回 | 本计划第 3 步 |

结论：不靠网关也能做出 6 个有真实数据的页面；「会话 / 用量 / 路由 / 供应商」这四组
要做到 magpie 那种完整度，依赖二期网关。两者可以并行：先交付无网关版，二期网关落地后
把路由与请求级用量接上同一套导航。
