# Context Lifecycle 下一版本规划

> 工作项：`context-lifecycle-next-version-planning`
> 状态：规划完成，等待实施批准
> 范围：能力集成决策、竞品组合筛选、版本定位、架构调整与发布规划
> 非目标：本工作项不直接实施产品代码

## 目标

产出一份可以直接决策的下一版本方案，明确回答：

1. 哪些现有能力或竞品机制可以直接集成，哪些需要适配后集成，哪些不应采用。
2. 哪些竞品继续作为核心参考，哪些降为低频专项观察，哪些退出主动跟踪。
3. 下一版本的定位、功能范围、架构调整、兼容策略、发布顺序和验收方法。

```text
W0 锁定现有能力基线
 ├── W1 能力集成决策矩阵 ─┐

                           ↓
```

- `W6` 是面向用户的最终决策面，不得残留需要用户代替团队判断的技术选项。

## 工作项

### W0——锁定现有能力基线

**输入**

- 当前竞品报告和观察清单。
- 当前仓库状态与已经对外生效的行为。

**输出**

- 一份不得退化的现有能力清单，包括：memo 时间语义、context offload 引用、continuity、handoff、role memory、Rex 工作项、dry-run readiness 和现有 CLI 兼容性。

**完成条件**

- 每项建议都必须说明扩展哪个现有模块；若无法复用，必须说明现有边界为什么不合适。
- 方案不以新增向量数据库、图数据库或远程服务为前提。

**验证证据**

- 引用的现有源码路径真实存在。
- 69 个定向测试继续作为行为基线。

**回退点**

- 如果无法无歧义地描述现有基线，则停止后续竞品与版本决策，先解决基线问题。

### W1——能力集成决策矩阵

**依赖**：`W0`

**输出**

对每项候选能力做以下分类：

- `direct-integrate`：现有抽象已经拥有该行为，可以直接扩展；
- `adapt-and-integrate`：能力有价值，但必须适配现有 schema、权限或生命周期；
- `observe-only`：值得继续观察，但不应进入本版本；
- `reject`：与 local-first、安全或可维护性目标冲突，不采用。

矩阵至少覆盖：

- 来源与使用证据回执；
- scope 与 ACL 的分离；
- 可靠摄入、幂等与重放；
- Context Impact Set / ExecutionContextPacket；
- 过期读取与写前预检；
- `full → summary+ref → ref-only` 预算降级；
- 可验证压缩；
- 带 revision 的 handoff 与修改后对账；
- 预测式 anticipation 与图检索。

**完成条件**

- 每行都包含能力价值、AIOS 当前基线、归属模块、兼容风险、工作量和验收证据。
- 只有双方契约真正匹配时，才能标为直接集成。

**验证证据**

- 每个 P0/P1 项都同时提供“当前项目模块 ↔ 竞品源码”的双侧证据。
- planning、contextdb、memo、offload、harness 之间不得出现重复所有权。

**回退点**

- 证据不足的能力一律降为 `observe-only`，不得为了证明其价值而扩大版本范围。

### W2——竞品组合筛选

**依赖**：`W0`

**输出**

将全部竞品划分为四档：

- `core-reference`：核心参考；相关能力变化时主动做源码评审；
- `specialist-reference`：专项参考；只保留一个窄能力，低频检查；
- `archive-reference`：归档参考；保留历史证据，不再定期刷新；
- `remove`：移出主动观察清单；没有剩余的独特价值。

**完成条件**

- 每个保留项目都必须有一个明显优于其他项目的唯一参考问题。
- 仅因知名度、生态规模或已经被吸收的基础能力而保留的项目必须降级。
- 每个保留项目都要明确刷新频率和触发条件。

**验证证据**

- 当前 12 个竞品全部获得明确档位和理由。
- 核心参考项目数量必须足够少，保证后续能够真正做深度源码评审。

**回退点**

- 两个项目回答同一问题时，保留证据更强的项目，另一个归档；只有能提供独立安全反例时才例外保留。

### W3——下一版本定位

**依赖**：`W1`、`W2`

**输出**

用一句话定义产品定位，并给出严格的版本边界，包括：

- 用户可感知的结果；
- 本版本功能；
- 明确非目标；
- 单用户与 Team 就绪边界；
- 数据迁移和兼容承诺。

**完成条件**

- 不提竞品名称也能理解这个版本解决什么问题。
- 用户可见能力组不超过三个。
- 安全前置条件与可选智能能力必须分开。

**验证证据**

- 每个版本内功能都能对应 W1 矩阵中的能力和当前真实痛点。
- 每个非目标都有明确的后续触发条件，而不是无限期承诺。

**回退点**

- 如果版本需要超过三个用户可见能力组，则拆分版本，不能把额外范围隐藏在“架构调整”中。

### W4——目标架构与兼容策略

**依赖**：`W3`

**输出**

- 明确 ContextItem/Provenance、ContextCard、ExecutionContextPacket、ContextReceipt、压缩回执和 handoff lineage 的唯一归属模块。
- 描述 `工作项 → 上下文装配 → 写前预检 → 修改 → 修改后对账 → handoff/压缩` 的完整数据流。
- 为现有 memo、continuity、handoff 和 plan v2 数据设计兼容适配与迁移方式。
- 明确 shadow mode 以及 fail-open / fail-closed 的边界。

**完成条件**

- 现有公开命令和已存数据继续可读。
- 不新增一套平行 handoff 或 memory 协议。
- ACL、来源和 revision 在 prompt 文本以下的系统层执行，不能依赖模型自觉遵守。
- `subagent-runtime/context-packet.mjs` 保持为薄适配层，不能成为通用协议所有者。

**验证证据**

- 架构图明确列出 writer、reader、状态路径和强制执行点。
- 实施前已经明确迁移测试与回滚点。

**回退点**

- 如果一个新抽象不能同时服务 planning、solo runtime 和 Team handoff，则把行为留在原归属模块，不创建泛化框架。

### W5——发布阶段与验收门

**依赖**：`W4`

**输出**

分阶段发布：

1. P0 安全修复。
2. 只观察、不改变行为的 ContextReceipt 和 ExecutionContextPacket。
3. shadow 模式的上下文预检与修改后对账。
4. 仅对计划型和高风险写入启用选择性阻断。
5. 只有安全、权限和并发测试通过后，才开放 Team/shared-canonical 能力。

**完成条件**

- 每个阶段都有启用/关闭方式、迁移行为、指标、成功阈值和回滚方案。
- 观察阶段不得改变现有模型输入、写入判断和工作流结果。

**验证证据**

- required-context 与 fresh-context 覆盖率目标。
- 跨 Agent supersede、ACL 粘性、并发 append、过期写入、压缩保真和 handoff 重验证场景。

**回退点**

- 任何无法接受的误报或兼容性退化，都必须能退回 shadow mode，且不破坏已有存储状态。

### W6——一页式最终决策

**依赖**：`W5`

**输出**

一份只包含以下内容的简洁方案：

- 这次到底建设什么；
- 保留哪些现有能力；
- 现在集成哪些能力；
- 哪些能力暂缓或拒绝；
- 哪些竞品继续主动参考；
- 版本范围、顺序、工作量和 go/no-go 验收门。

**完成条件**

- 用户不需要阅读源码报告，就能批准、缩小或否决该版本。
- 不把未解决的技术选择交给用户代替团队判断。

**验证证据**

- 每条结论都能追溯到 `W1`～`W5` 的决策。
- 最终只给一个推荐默认方案，不提供一组看似平级的选项菜单。
